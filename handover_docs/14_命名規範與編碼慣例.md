# 🏷️ 文檔十四：命名規範與編碼慣例 (Naming Conventions Specification)

> **目的**：確立高雄青職「活力同行」全系統命名之單一真理來源，徹底杜絕歷史別名、拼寫分歧與語意模糊，確保團隊協同一致性。  
> **適用範疇**：全體微服務（Core、Progression、Chat）、前端客戶端（WebApp SPA）、試算表儲存層與自動化測試套件。

---

## 1. 命名哲學與基本命名法

全系統貫徹以下四項核心命名原則：

1. **唯一真相原則 (Single Canonical Name)**：同一語意概念在前端、後端各微服務、RPC 傳輸及試算表欄位中，**必須且僅能有一個標準名稱**。新版架構嚴禁在程式碼中擴散自創縮寫或舊名容錯。
2. **語意精確性 (Semantic Explicitness)**：優先使用自解釋性強的完整單詞，嚴禁模糊縮寫（例如：`playerId` 嚴禁縮寫為 `pId` 或 `username`；`groupId` 嚴禁縮寫為 `gId`）。
3. **區分視圖表現與實體資料**：DTO 與儲存資料只傳遞純粹業務語意資料，不混入客戶端視圖裝飾前綴。
4. **命名格式規則表**：

| 場景 | 命名格式 | 範例 | 說明 |
| :--- | :--- | :--- | :--- |
| **JSON 物件屬性** | `camelCase` 小駝峰 | `playerId`, `birthYear`, `joinGroupTime` | 前後端資料傳輸與 DTO 唯一規範 |
| **Action 路由動作** | `camelCase` 小駝峰 | `submitDailyPractice`, `getProgressBundle` | 動詞開頭，精確表達操作目的 |
| **TypeScript / 類別** | `PascalCase` 大駝峰 | `PlayerProfile`, `GroupSummaryData` | 介面、型別與類別定義 |
| **常數與枚舉** | `UPPER_SNAKE_CASE` 全大寫 | `STATUS_ACTIVE`, `MAX_GROUP_MEMBERS` | 系統限制與設定檔鍵值 |
| **試算表表頭 (Row 1)** | `camelCase` 小駝峰 | `playerId`, `matrixColIndex`, `lastLoginAt` | 與 JSON DTO 保持一對一語意映射 |
| **快取鍵值 (CacheKey)** | 冒號階層前綴大寫 | `CACHE:CORE:ENV`, `CACHE:CHAT:GROUP:G_01` | 名稱空間防止跨微服務碰撞 |
| **HTML DOM ID** | `camelCase` 小駝峰 | `homeGroupScoreText`, `homePersonalScoreText` | 前端視圖 DOM 節點識別碼，強制視圖前綴 |
| **CSS 樣式類別** | `kebab-case` 連字號小寫 | `hero-score-grid`, `hero-group-score` | 語意化組件樣式類別命名 |
| **前端 View / Store 類別** | `PascalCase` 大駝峰 | `DashboardView`, `PracticeStore` | 前端視圖控制器與狀態管理容器類別 |

## 2. 核心領域實體與識別碼命名

### 2.1 使用者身分相關 (`Player`)

| 概念 | 標準名稱 (Canonical) | 淘汰之舊名稱 (Deprecated) | 型別 | 規範定義與驗證規則 |
| :--- | :--- | :--- | :---: | :--- |
| **使用者帳號識別碼** | `playerId` | `username`, `identifier`, `cleanUser`, `pId` | `string` | 英數、小寫字母、底線、點或連字號。全系統使用者唯一主鍵。比對時一律強制 `toLowerCase()`。 |
| **顯示暱稱** | `name` | `displayName`, `regName`, `userName` | `string` | 於遊戲介面、排行榜與交流板顯示的聖徒稱呼（長度 1~20 字元）。 |
| **真實姓名** | `realName` | `trueName`, `actualName` | `string` | 實體名冊行政聯絡使用，選填，預設為空字串 `""`。 |
| **性別代碼** | `gender` | `userGender`, `sex` | `string` | **嚴格限定枚舉**：`'BROTHER'` \| `'SISTER'`。 |
| **出生年份** | `birthYear` | `birth`, `bornYear`, `birthday` | `number` \| `null` | **數值型西元年**（$1900 \le \text{birthYear} \le \text{currentYear}$）。未填為 `null`，禁存空字串。 |
| **聯絡手機** | `phone` | `mobile`, `tel`, `phoneNumber` | `string` | 純字串型態，保留開頭 `0` 或國碼 `+886`。 |
| **頭像路徑** | `avatarUrl` | `avatar`, `avatarKey`, `avatarGender`, `avatarNo` | `string` | 完整相對路徑字串，如 `../avatar-male/avatar-male-direct-005.png`。 |
| **個人矩陣直欄索引** | `matrixColIndex` | `colIndex`, `matrixCol`, `userColIndex` | `number` | 整數，對應 `DailyMatrix` 與 `MeetingMatrix` 的欄號（$\ge 2$）。 |

### 2.2 活力組組織相關 (`Group`)

| 概念 | 標準名稱 (Canonical) | 淘汰之舊名稱 (Deprecated) | 型別 | 規範定義與驗證規則 |
| :--- | :--- | :--- | :---: | :--- |
| **活力組唯一識別碼** | `groupId` | `gId`, `targetGroupId`, `vitalGroupId` | `string` | 格式為 `GRP_<8碼UUID>`，未入組時為空字串 `""`。全系統禁止使用 `targetGroupId`。 |
| **小組名稱** | `groupName` | `name`, `teamName` | `string` | 小組自訂隊名（長度 2~20 字元）。 |
| **邀請碼** | `inviteCode` | `invCode`, `code` | `string` | 6 碼或 8 碼大寫英數組合成員邀請碼。 |
| **組長帳號** | `leaderPlayerId` | `leaderId`, `leader`, `newLeaderPlayerId` | `string` | 組長的 `playerId`。入站傳參與出站回傳一律為 `leaderPlayerId`。 |
| **入組日期** | `joinGroupTime` | `joinTime`, `joinedAt` | `string` | 格式固定為 `YYYY-MM-DD`（如 `2026-09-28`）。 |
| **小組人數** | `memberCount` | `membersCount`, `totalMembers` | `number` | 當前有效組員數量（上限為系統全域常數 5 人）。 |
| **活躍成員索引字典** | `activeMembers` | `activeMembersJson`, `membersMap` | `Record<string, number>` | 鍵為小寫 `playerId`，值為其在操練矩陣之直欄索引 (`matrixColIndex` $\ge 2$)，例如 `{"user1": 2, "user2": 3}`。嚴禁儲存為陣列。 |
| **留言矩陣直欄索引** | `postsColIndex` | `colIndex`, `messageColIndex`, `hintCol` | `number` | 整數，對應 `GroupMessageMatrix` 直欄（$\ge 2$）。 |

### 2.3 組織區域劃分 (`District` & `Area`)

* **照顧區 (6大區)**：`district`（範例：`'東'`, `'西'`, `'中'`, `'南A'`, `'南B'`, `'北'`）。
* **大區 (45個區)**：`area`（範例：`'昌裕'`, `'新苓'`, `'博愛'`）。

### 2.4 實體在線與生命週期狀態 (`Status`)

```typescript
// 全系統實體通用生命週期狀態（除 AreaMappings isEnabled 外，所有分頁與實體全面統一為二元狀態）
type EntityStatus = 'ACTIVE' | 'INACTIVE';

// 使用者帳號狀態（停權、停用與軟刪除全面收斂為 INACTIVE）
type PlayerStatus = EntityStatus;

// 活力組狀態（小組解散全面收斂為 INACTIVE，原 DISBANDED 已全面淘汰）
type GroupStatus = EntityStatus;

// 公告狀態（公告下架或過期全面收斂為 INACTIVE，原 ARCHIVED 已全面淘汰）
type AnnouncementStatus = EntityStatus;

// 規則與配置狀態（里程碑、篇章、寶箱、任務卡片啟用/停用）
type ConfigStatus = EntityStatus;
```

## 3. 分數、數值與進度命名規範

### 3.1 點數命名字典（終結歷史割裂）

新架構**徹底廢止模糊的 `totalScore`、`totalPoints`、`earnedPoints` 與 `addedPoints`**，點數體系精確收斂為以下具名定義：

| 欄位名稱 (Canonical) | 淘汰之舊名稱 (Deprecated) | 型別 | 語意說明與計算公式 |
| :--- | :--- | :---: | :--- |
| `personalPoints` | `totalScore`, `totalPoints`, `userPoints` | `number` | 個人生涯歷年總積分（$\text{sumHistoryPoints(historySummary)} + \text{settledTotalScore}$）。前端儀表板英雄卡下半部 (`#homePersonalScoreText`) 綁定之個人累積總分來源。 |
| `settledTotalScore`<br/>*(DB Col 5 / 快照鏡像 `currentYearPoints`)* | `yearPoints`, `activePoints`, `score`, `totalScore` | `number` | **個人當前自然年度累計結算分數**（`PlayerProgress` Col 5 實體儲存，包含每日操練、每週聚會、個人里程碑/寶箱成就、特殊任務與個人特殊獎勵）。 |
| `joinBaseScore`<br/>*(DB Col 6 / DTO 鏡像 `joinBasePoints`)* | `baseScore`, `base` | `number` | **個人加入目前活力組時之結算基準分**（`PlayerProgress` Col 6 實體儲存；入組扣除點，確保歷史操練與獲獎不回溯；退組/調組時重新錨定當前結算分）。 |
| `contributionPoints` | `contributionScore`, `myContribution` | `number` | 個人在當前活力組內的活躍操練與個人獎勵貢獻分（$\max(0, \text{settledTotalScore} - \text{joinBaseScore})$）。首頁點數面板相容隱藏節點 (`#homeContributionText`) 綁定此值。 |
| `groupTotalPoints` | `groupScore`, `teamTotalScore` | `number` | 小組歷年累計總積分（含歷任組員在籍期間之沉澱歷史分數與在籍組員貢獻分：$\text{sumHistoryPoints(Group Col 2)} + \sum_{m \in \text{ActiveMembers}} \text{contributionPoints}_m$）。前端儀表板英雄卡上半部 (`#homeGroupScoreText`) 綁定之小組總分來源。 |
| `cooperativePoints` | `activeGroupScore`, `sharedPoints` | `number` | 小組當年度當前在籍組員共同創造的活力分（$\sum_{m \in \text{ActiveMembers}} \text{contributionPoints}_m$）。 |
| `journeyPoints` | `expPoints`, `chapterProgress` | `number` | 用於推進屬靈美德篇章晉級之有效累計點數。 |
| `gapPoints` | `pointsToNext`, `diff`, `gap` | `number` | 距離推進至下一篇章門檻尚缺之點數差額（滿級為 0）。 |
| `deltaPoints` | `earnedPoints`, `addedPoints`, `points` | `number` | **單次操作之點數增量**（打卡獲得、獎勵發放之增量點數，如 `+30`）。 |

### 3.2 貢獻度字典與進度欄位約束

* **成員貢獻度字典**：`memberContribution`（型別 `Record<string, number>`，鍵為 `playerId`，值為其組內貢獻點數 `contributionPoints`）。
* **歷史年度封存摘要與控制鍵**：`historySummary`（型別 `Record<string, any>`，平鋪包含歷年封存分數與排程控制鍵）：
  * **`PlayerProgress` Col 2（個人歷程）語意約束**：
    * 僅儲存歷年已封存之往年年度總分（如 `{"2024": 500, "2025": 800}`）與系統排程控制鍵（以底線 `_` 開頭：`_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`）。
    * ⚠️ **【鐵律約束】嚴禁將當前年度個人獎勵（如 `"2026": 840`）寫入 `PlayerProgress.historySummary`！** 當年度所有個人獎勵（個人里程碑、成就寶箱、特殊任務、管理員特權發放）一律結算並累加至 Col 5 `settledTotalScore`。
  * **`GroupProgress` Col 2（小組歷程）語意約束**：
    * 儲存小組歷年累積總分與小組獎勵沉澱（如 `{"2026": 3400}`）。小組篇章晉級獎勵與管理員發放之小組特殊獎勵，維持寫入此處。
* **當年度累計結算分**：`settledTotalScore`（`PlayerProgress` Col 5，型別 `number`，整數 $\ge 0$）。排程與個人獎勵結算後的權威累計分，供前端、小組貢獻計算與總帳 $O(1)$ 秒開讀取。
* **入組基準分**：`joinBaseScore`（`PlayerProgress` Col 6，型別 `number`，整數 $\ge 0$）。入組時錨定為當時之 `settledTotalScore`，退組/調組時重新錨定。
* **里程碑清單**：`milestones`（型別 `MilestoneRecord[]`，包含已達成里程碑之識別代碼 `id`、獲得點數 `reward` 與完成時間戳 `completedAt`，全面廢除歷史冗餘鍵 `achievedAt`）。

## 5. 時間、日期與格式命名鐵律

1. **純日曆日期 (`date`)**：
   * 格式：`YYYY-MM-DD`（如 `2026-10-14`）。時區以台灣 GMT+08:00 為唯一基線。
2. **紀元週次識別碼 (`weekKey`)**：
   * 格式：`YYYY-Www`（如 `2026-W42`），嚴格遵循 ISO-8601 週四定年原則。週一為起始，週日為截止。
3. **時間欄位後綴鐵律**：
   * **字串時間**：一律以 `*At` 結尾（如 `createdAt`, `updatedAt`, `lastLoginAt`, `respondedAt`），格式為帶明確時區之 ISO-8601 字串。
   * **數值毫秒**：一律以 `*TimeMs` 結尾或命名為 `timestamp`（如 `sinceTimeMs`），型別為 13 碼整數。

## 6. 後端 Action 動詞家族規範

Action 統一採用小駝峰 `camelCase`，動詞嚴格受限於標準動詞家族：
* `get`：冪等讀取單一或聚合資源（如 `getProfile`, `getPractice`, `getBootstrap`, `getAppConfigs`）
* `submit`：客戶端提報數據驗證與寫入（如 `submitDailyPractice`, `submitMeetingPractice`）
* `post`：發布新訊息（如 `postMessage`）
* `create`：建立全新實體（如 `createGroup`, `createAnnouncement`）
* `join` / `leave`：加入或離開群組（如 `joinGroup`, `leaveGroup`）
* `update`：異動實體屬性（如 `updateAvatar`, `updatePassword`）
* `delete`：刪除特定實體或留言（如 `deleteMessage`）
* `transfer`：移交權限或組長職責（如 `transferGroupLeader`）
* `set`：設定或覆寫指定配置/公告（如 `setGroupAnnouncement`）
* `sync`：微服務間狀態校準（如 `syncGroupMembership`）
* `settle`：離隊或特定節點點數結算（如 `settleMemberDeparture`）
* `archive`：週期結束凍結結算（如 `archiveAnnualGroupProgress`）
* `clear`：清理快取或清空容器（如 `clearSystemCache`, `clearGroupChat`, `clearGroupAnnouncement`）
* `run`：執行背景排程批次運算（如 `runDailyMilestoneSettlement`）
* `evaluate`：條件引擎判定邏輯（如 `evaluateTargetMilestones`）
* `grant`：特權發放點數獎勵（如 `grantTargetedReward`）
* `login` / `register` / `ping`：認證與連線基礎端點

### 7.2 核心進度帳本欄位語義約束 (`PlayerProgress` vs `GroupProgress`)

在進度帳本設計中，個人與小組之進度表具備嚴格的語義劃分與物理邊界，嚴禁混淆：

| 欄位名稱 | `PlayerProgress` 直欄與語義約束 | `GroupProgress` 直欄與語義約束 |
| :--- | :--- | :--- |
| **Col 1 (主鍵)** | `playerId`：聖徒帳號唯一主鍵。 | `groupId`：活力組唯一主鍵。 |
| **Col 2 (`historySummary`)** | **【個人歷程封存】**：<br/>- 僅儲存往年已封存年度總分（如 `{"2024": 500, "2025": 800}`）與系統排程控制鍵（以 `_` 開頭：`_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`）。<br/>- ⚠️ **【鐵律約束】嚴禁寫入當前年度個人獎勵點數！** 當年度個人獎勵一律結算入 Col 5。 | **【小組歷史總分與沉澱】**：<br/>- 儲存小組歷年累積總分與小組獎勵沉澱（如 `{"2026": 3400}`）。<br/>- 小組篇章解鎖獎勵與管理員發放之小組特殊獎勵，維持寫入此處。 |
| **Col 3 (`milestones`)** | `milestones`：個人已領取之里程碑與寶箱陣列 JSON。 | `milestones`：小組已解鎖之篇章陣列 JSON。 |
| **Col 4 (`updatedAt`)** | `updatedAt`：最後更新時間戳 (ISO-8601)。 | `updatedAt`：最後更新時間戳 (ISO-8601)。 |
| **Col 5 (`settledTotalScore`)** | **`settledTotalScore`**：**當前自然年度累計結算分數**（包含每日操練、每週聚會、個人里程碑/成就寶箱、特殊任務與個人特殊獎勵）。供前端與總帳 $O(1)$ 秒開讀取。 | *無此直欄*（小組總分由動態公式即時計算：Col 2 歷年沉澱分 + 在籍組員組內貢獻分）。 |

### 7.3 試算表批次讀寫寬度慣例 (Spreadsheet Write Range Width Specification)

Google Apps Script 的試算表寫入 API 以矩陣維度（`getRange(row, col, numRows, numCols).setValues(matrix)`）為基礎。為保證資料庫完整性，系統對進度表寫入寬度制定了不可逾越的鐵律：

#### 1. `PlayerProgress` 批次寫入範圍：Col 2 ~ Col 5（欄寬 4）
* **寫入起始點**：Col 2 (`historySummary`)。
* **寫入欄寬**：**4 欄**（涵蓋 Col 2 `historySummary`, Col 3 `milestones`, Col 4 `updatedAt`, Col 5 `settledTotalScore`）。
* **標準寫入語法**：
  ```javascript
  targetSheet.getRange(rowInfo.rowIndex, 2, 1, 4).setValues([[
    JSON.stringify(rowInfo.historySummary || {}),
    JSON.stringify(milestones),
    nowIso,
    rowInfo.settledTotalScore
  ]]);
  ```
* 🛡️ **【Col 6 物理隔離防護】**：
  * 批次更新範圍**絕對不可擴展至第 6 欄**！
  * Col 6 (`joinBaseScore`) 屬於成員組織關係生命週期欄位，僅限於調組或退組生命週期 (`syncGroupMembership` / `settleMemberDeparture`) 中由專門函式以單元格方式精確更新 (`getRange(row, 6).setValue(...)`)。日常排程與獎勵發放嚴格禁止觸碰 Col 6。

#### 2. `GroupProgress` 批次寫入範圍：Col 2 ~ Col 4（欄寬 3）
* **寫入起始點**：Col 2 (`historySummary`)。
* **寫入欄寬**：**3 欄**（涵蓋 Col 2 `historySummary`, Col 3 `milestones`, Col 4 `updatedAt`）。
* **標準寫入語法**：
  ```javascript
  groupSheet.getRange(gInfo.rowIndex, 2, 1, 3).setValues([[
    JSON.stringify(gd.updatedHistorySummary || {}),
    JSON.stringify(gd.updatedMilestones || []),
    nowIso
  ]]);
  ```

## 8. 編碼慣例與反模式守則 (Coding Conventions & Anti-patterns)

### 8.1 帳本與點數處理反模式 (Anti-patterns)

#### ❌ 反模式 1：個人獎勵寫入 `historySummary` 年份鍵 (Personal Reward in HistorySummary)
* **錯誤示範**：個人獲獎時，無差別呼叫 `depositToHistorySummary(historySummary, pts, yearStr)`，將個人獎勵寫入 `PlayerProgress` Col 2 的 `historySummary["2026"]`。
* **破壞性後果**：個人對小組貢獻分公式為 $\max(0, \text{settledTotalScore} - \text{joinBaseScore})$。若個人獎勵寫入 Col 2，Col 5 的 `settledTotalScore` 完全未增長，導致組員在籍期間達成的所有個人成就與特殊獎勵無法帶動個人小組貢獻分，小組總分也無法反映組員的個人卓越追求，造成分數割裂。
* **正確做法**：
  * **純領域分流**：在 `MilestoneEngine.evaluate` 中，小組獎勵 (`GROUP`) 寫入 `historySummary`；個人獎勵 (`PLAYER`) 累加至 `updatedSettledTotalScore`，`PlayerProgress.historySummary` 保持原樣不變。
  * **帳本持久化**：在 `ProgressLedger.depositReward` 與 `batchApplyMilestoneSettlements` 中，個人獎勵直接累加寫入 Col 5 `settledTotalScore`。

#### ❌ 反模式 2：試算表寫入範圍過寬盲目覆寫 Col 6 (Blind Wide Range Overwrite)
* **錯誤示範**：在更新 `PlayerProgress` 時，使用大於 4 欄的寫入寬度（如 `getRange(row, 2, 1, 5)` 或全行覆寫 `getRange(row, 1, 1, 6)`）卻未傳入或計算正確的 `joinBaseScore`。
* **破壞性後果**：Col 6 `joinBaseScore` 被意外覆寫為 `0`、`null` 或未定義值，導致該組員加入小組前的歷史操練與獎勵瞬間被全部當成當前組內貢獻分暴增，徹底摧毀點數守恆定律與組織公正性。
* **正確做法**：日常排程與獎勵持久化寫入寬度嚴格限制為 4 欄（Col 2~5），杜絕任何對 Col 6 的越界寫入。

#### ❌ 反模式 3：夜間結算同晚小組總分快照脫節 (Stale Group Snapshot)
* **錯誤示範**：在批次評估排程中，迴圈開始前預先提取了小組總分快照 `groupScoreMap`，當某組員在當晚獲得個人里程碑獎勵時，僅更新了個人記憶體分數，未同步累加 `groupScoreMap[pGid]`。
* **破壞性後果**：同晚緊接著在下方執行的小組篇章評估讀取的是過時的舊總分。即使該組員獲得的獎勵點數已足以讓小組跨過篇章門檻，當晚小組也無法解鎖新篇章，必須等待下一次總分更新，造成體驗滯後。
* **正確做法**：當組員達成個人里程碑獲獎時，除同步 `pRowInfo.settledTotalScore` 外，必須即時原子累加 `groupScoreMap[pGid] += Number(pDec.totalRewardPoints)`，確保同晚小組篇章即時解鎖。

#### ❌ 反模式 4：日常排程夾帶歷史資料遷移邏輯 (Polluting Daily Schedule with Migration)
* **錯誤示範**：在常態每日午夜排程 `executeDailySettlement` 中每次執行歷史年份鍵檢查與搬移邏輯。
* **破壞性後果**：增加常態排程的 I/O 開銷、執行時間與出錯風險，違背單一職責原則。
* **正確做法**：日常排程保持純淨；歷史資料遷移應實作為獨立的一次性遷移函式（如 `runMigratePlayer2026Rewards()`），由管理員手動執行並具備嚴格冪等性（已搬移後重複執行為 0 異動）；遷移完成並驗收後，及時清理過渡代碼。

#### ❌ 反模式 5：缺乏型別防護直接加算數值 (String Concatenation & NaN Escape)
* **錯誤示範**：直接以 `pInfo.settledTotalScore + pts` 或字串拼接方式計算點數。
* **破壞性後果**：若試算表儲存格為空或字串格式，引發 `"100" + 50 = "10050"` 或 `undefined + 50 = NaN` 逃逸，毀損試算表數值。
* **正確做法**：全面使用 `Number(val) || 0` 進行防禦性轉型，杜絕任何 `NaN` 逃逸與型別隱患。

### 8.2 領域邏輯與架構編碼慣例 (Architectural Conventions)

1. **純領域模組零 I/O (Pure Domain Decoupling)**：
   * 領域計算引擎（如 `MilestoneEngine.evaluate`）專注於記憶體決策物件產出，嚴禁直接呼叫 Google Sheets API 或產生外部副作用。
2. **記憶體與持久化層狀態零漂移 (Zero Drift)**：
   * 帳本層在批次更新試算表的同時，必須同步更新記憶體中的字典快照物件（如 `pInfo.settledTotalScore = newSettledScore`），保證批次後續流程即時感知最新狀態。
3. **點數守恆與生命週期三定理 (Conservation of Points Invariants)**：
   * **入組前不回溯**：未入組聖徒獲得的操練分與個人獎勵，在加入活力組時由 `joinBaseScore` 完整錨定截斷，入組瞬間個人貢獻分嚴格為 0，絕不灌水給新組。
   * **在組同心累積**：在組期間獲得的個人操練與個人獎勵全額累加至 Col 5 `settledTotalScore`，等額帶動個人小組貢獻分與小組總分增長。
   * **退組自動沉澱**：組員退組時，其在組期間貢獻之分數全額沉澱至舊組 `GroupProgress.historySummary`，舊組總分守恆不失分；退組後 `joinBaseScore` 重新錨定為當前總分，隨後加入新組時貢獻分重新從 0 起算，絕不跨組轉移。
   * 詳情與完整測試驗證紀錄請參閱：[reward_change_record.md](file:///d:/Antigravity%20workspaces/高雄青職專案/reward_change_record.md)。
4. **前端快取版本號同步升級鐵律 (Strict Cache-Busting Versioning)**：
   * 每次前端代碼（HTML/CSS/JS）發生重大改版，必須同步將 `src/frontend/html/sw.js` 中的 Service Worker 快取名稱升級（當前為 `vital-cache-v104`），並同步更新 `index.html` 內所有 `<script>` 與 `<link>` 引用之查詢字串版本號（如 `?v=20261014-v104`），確保用戶端 PWA 與瀏覽器強制刷新生效，杜絕舊代碼粘滯。
