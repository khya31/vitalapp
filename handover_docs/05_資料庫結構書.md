# 文檔五：資料庫結構書 (Database Schema Specification)

> **目的**：作為全專案三大微服務試算表實體結構、所有分頁工作表 Schema、直欄映射常數與 Base-100 打包演算法的**唯一完整真理權威**。  
> **關聯檔案**：`src/backend/bootstrapDatabase.js`（一鍵初始化精靈）、`dist/*/Code.gs`（生產端存取）。  
> **版本規範**：v104 (20261014-v104 / 基準測試 589/589 PASS)。  
> **更新記錄**：2026-10-14（同步首頁右上角點數面板改版、小組累積總點數與個人整年總點數之資料庫欄位投影與視圖呈現一致性規範）。

---

## 1. 三大物理資料庫概覽與職責隔離

系統採用三張獨立的 Google Sheets 試算表達成物理資料庫隔離：

| 資料庫代號 | 試算表名稱 | 服務綁定 | 涵蓋工作表清單 | 讀寫特性與鎖定機制 |
| :--- | :--- | :---: | :--- | :--- |
| **Core DB** | 核心業務資料庫 | 微服務 A (`dist/core`) | `Players`, `Groups`, `DailyMatrix`, `MeetingMatrix`, `Announcements`, `AdminLogs`, `AreaMappings`, `環境變數` | **打卡無鎖直寫**（20~50ms），註冊與退組具 10s `LockService` 排他鎖保護。 |
| **Chat DB** | 小組交流獨立庫 | 微服務 B (`dist/chat`) | `GroupMessageMatrix` | 專屬 3000ms 微鎖等待逾時，直欄矩陣拓撲，一組一快取。 |
| **Progression DB** | 成就履約獨立庫 | 微服務 C (`dist/progression`) | `PointsConfig`, `MilestonesConfig`, `ChapterConfig`, `AchievementConfig`, `TasksConfig`, `PlayerProgress`, `GroupProgress`, `TaskClaims` | 深夜密集批次運算，純領域排程結算，總帳審計。 |

## 2. 核心業務資料庫 (Core DB) 工作表完整 Schema

### 2.1 `Players`（聖徒名冊實體表 — 嚴格 21 欄 Col A ~ Col U）
後端存取嚴格依循 1-based 直欄常數：

```javascript
const PLAYERS_COLUMNS = {
  PLAYER_ID: 1,        // Col A: playerId (帳號主鍵，小寫英數)
  PASSWORD_HASH: 2,    // Col B: passwordHash (SHA-256 加鹽雜湊)
  SALT: 3,             // Col C: salt (16 碼隨機鹽值)
  AVATAR: 4,           // Col D: avatar (表頭名為 avatar，別名 AVATAR_KEY，DTO 輸出為 avatarUrl)
  REAL_NAME: 5,        // Col E: realName (真實姓名，純文字 @ 格式)
  NAME: 6,             // Col F: name (顯示暱稱，純文字 @ 格式)
  GENDER: 7,           // Col G: gender ('BROTHER' | 'SISTER')
  BIRTH_YEAR: 8,       // Col H: birthYear (西元年整數，未填為 null)
  PHONE: 9,            // Col I: phone (手機字串，純文字 @ 格式)
  DISTRICT: 10,        // Col J: district (照顧區，別名 CARE_DISTRICT)
  AREA: 11,            // Col K: area (大區名稱，別名 CARE_AREA)
  RESERVED_1: 12,      // Col L: _reserved_1 (保留緩衝欄位)
  GROUP_ID: 13,        // Col M: groupId (所屬活力組 ID，未入組為空字串)
  MATRIX_COL_INDEX: 14,// Col N: matrixColIndex (雙矩陣直欄座標 >= 2)
  JOIN_GROUP_TIME: 15, // Col O: joinGroupTime (入組時間 YYYY-MM-DD，純文字 @ 格式)
  RESERVED_2: 16,      // Col P: _reserved_2 (保留緩衝欄位)
  CREATED_AT: 17,      // Col Q: createdAt (註冊時間戳 ISO-8601)
  LAST_LOGIN_AT: 18,   // Col R: lastLoginAt (最後登入時間戳 ISO-8601)
  STATUS: 19,          // Col S: status ('ACTIVE' | 'INACTIVE')
  RESERVED_3: 20,      // Col T: _reserved_3 (保留緩衝欄位)
  RESERVED_4: 21       // Col U: _reserved_4 (保留緩衝欄位)
};
```

### 2.2 `Groups`（活力組名冊表 — 10 欄 Col A ~ Col J）

| 直欄 | 欄位代碼 | 1-based 索引 | 資料型別 | 範例與說明 |
| :---: | :--- | :---: | :--- | :--- |
| **Col A** | `groupId` | 1 | `string` | 小組唯一主鍵（如 `GRP_a1b2c3d4`） |
| **Col B** | `groupName` | 2 | `string` | 小組名稱（長度 2~20 字元） |
| **Col C** | `inviteCode` | 3 | `string` | 入組邀請碼（6 碼或 8 碼大寫英數） |
| **Col D** | `leaderPlayerId` | 4 | `string` | 組長之 `playerId` |
| **Col E** | `historyPoints` | 5 | `number` | 歷年離隊成員沉澱之歷史總積分（整數 $\ge 0$） |
| **Col F** | `activeMembersJson`| 6 | `string` (JSON) | ⚠️ **在籍成員字典 JSON**（如 `{"user1": 2, "user2": 3}`，Key 為 playerId，Value 為 `matrixColIndex`；**嚴禁傳入 Array**，否則會被判定無效並回傳 `{}`） |
| **Col G** | `pinnedPostJson` | 7 | `string` (JSON) | 小組置頂公告 JSON（含 content, author, time） |
| **Col H** | `postsColIndex` | 8 | `number` | 對應 `GroupMessageMatrix` 直欄索引（$\ge 2$） |
| **Col I** | `status` | 9 | `string` | 狀態：`'ACTIVE'` 或 `'INACTIVE'`（原 `'DISBANDED'` 已全面統一收斂為 `'INACTIVE'`） |
| **Col J** | `createdAt` | 10 | `string` | 建立時間戳 (ISO-8601) |

### 2.3 【已廢除】`GroupMemberships`（成員任期歷程表 — 歷史歸檔）
* **廢除與移除記錄（2026-10-15）**：
  * **原設計定位**：早期曾預留作為成員多次調組之歷史審計流水表。
  * **架構淘汰原因**：全系統已全面改採 $O(1)$ 的「`joinBaseScore` 物理截斷與點數守恆架構」（在 Core DB 以 `Groups.historyPoints`、在 Progression DB 以 `GroupProgress.historySummary` 固化離隊成員貢獻分，以 `PlayerProgress.joinBaseScore` 錨定新基準分），組員調組時直接完成原子更新。
  * **物理清理完畢**：經確認全系統前後端（微服務 A/B/C、前端 PWA）均無任何讀寫依賴，最後一筆寫入停留在 2026-09-30。已於 2026-10-15 自線上 Core DB 物理刪除該工作表與使用說明表項目，Core 庫正式收斂為 8 張工作表。

### 2.4 `DailyMatrix`（每日操練矩陣）
* **拓撲結構**：X 軸為成員直欄（Col 2..N 為成員 `matrixColIndex`，Col 1 表頭為 `date`）；Y 軸為自 `2026-01-01` 起的連續自然日曆天（Row 2 為基準日）。
* **單元格值**：Base-100 打包整數（`0` ~ `1010101`）。

### 2.5 `MeetingMatrix`（每週聚會矩陣）
* **拓撲結構**：X 軸為成員直欄（Col 2..N 為成員 `matrixColIndex`，Col 1 表頭為 `weekKey`）；Y 軸為自 `2026-W01` 起依紀元連續週數排列。
* **單元格值**：Base-100 打包整數（`0` ~ `1010101`）。

### 2.6 `Announcements`（全召會系統公告表 — 7 欄 Col A ~ Col G）

* **直欄定義與規格**：
  | 直欄 | 欄位代碼 | 1-based 索引 | 資料型別 | 說明 |
  | :---: | :--- | :---: | :--- | :--- |
  | **Col A** | `announcementId` | 1 | `string` | 公告主鍵（如 `ANN_001`） |
  | **Col B** | `title` | 2 | `string` | 公告標題 |
  | **Col C** | `content` | 3 | `string` | 公告內文 |
  | **Col D** | `startDate` | 4 | `string` | 生效起始日 (`YYYY-MM-DD`) |
  | **Col E** | `endDate` | 5 | `string` | 生效截止日 (`YYYY-MM-DD`) |
  | **Col F** | `isPinned` | 6 | `boolean` | 是否置頂顯示（`TRUE` / `FALSE`） |
  | **Col G** | `status` | 7 | `string` | 狀態：`'ACTIVE'` 或 `'INACTIVE'`（下架封存統一為 `'INACTIVE'`） |

* **公告排序核心原則（免維護時間戳、零負擔）**：
  1. **第一優先級**：Col F `isPinned`（設為 `TRUE` 的置頂公告固定排在最前面展示）。
  2. **第二優先級**：**試算表自然列順序（Row Order / 由上而下的列順序，Row 2 在前、Row 3 在後）**。
  3. **管理員維運操作**：管理員若欲調整公告展示順序，直接在 Google Sheets 中調整列的上下位置（或將新公告插入在上方）即可，系統徹底廢除歷史 Col H `createdAt`，無需額外計算與維護數字序號。

## 3. 成就履約資料庫 (Progression DB) 8 張資料表完整 Schema

### 3.1 `PlayerProgress`（聖徒歷程與結算總表 — 6 欄標準 Col A ~ Col F）

| 直欄 | 欄位代碼 | 1-based 索引 | 資料型別 | 說明與資料範例 |
| :---: | :--- | :---: | :--- | :--- |
| **Col A** | `playerId` | 1 | `string` | 聖徒帳號唯一主鍵 |
| **Col B** | `historySummary` | 2 | `string` (JSON) | **歷年封存分數與排程中繼標記 JSON**：<br/>⚠️ **不再存儲當前年度個人獎勵點數！**（已於 2026-10-14 完成一次性遷移，將歷史 2026 鍵點數全額搬移至 Col 5 並清除鍵名）。<br/>本欄位**僅**存儲：<br/>1. 歷年封存分數（如往年 `{"2025": 500}`）<br/>2. 系統排程控制鍵（以底線 `_` 開頭）：`_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`。<br/>資料範例：<br/>`{"2025": 500, "_lastSettledDate": "2026-10-14", "_settledWeekKey": "2026-W42", "_settledMeetings": ["smallGroup", "lordDayMeeting"]}` |
| **Col C** | `milestones` | 3 | `string` (JSON) | 個人已解鎖里程碑與寶箱陣列 JSON：<br/>`[{"id": "CHEST_T1", "name": "初熟果子寶箱", "reward": 120, "completedAt": "2026-10-07T..."}]` |
| **Col D** | `updatedAt` | 4 | `string` | 最後更新時間戳 (ISO-8601) |
| **Col E** | `settledTotalScore` | 5 | `number` | **當前年度已結算總積分**（全量個人得分主帳本）：<br/>含每日操練累計 + 個人里程碑獎勵 + 個人成就寶箱 + 管理員個人特殊獎勵。<br/>深夜排程批次刷新、里程碑領取或特權發放時寫入，供前端與總帳 $O(1)$ 秒開讀取。<br/>個人歷年總分 = `settledTotalScore + sumHistoryPoints(historySummary)`（對應 DTO `personalPoints`，於首頁點數面板下半部 `#homePersonalScoreText` 呈現）。 |
| **Col F** | `joinBaseScore` | 6 | `number` | **入組基準分（小組貢獻時間截斷錨定分）**：<br/>加入當前活力組當下錨定之個人結算分（初始預設 0；調組或退組時重新錨定為當前 Col 5 `settledTotalScore`）。<br/>**在籍貢獻分** = $\max(0, \text{Col 5} - \text{Col 6})$（對應 DTO `contributionPoints`，同步至首頁隱藏元素 `#homeContributionText` 及同行貢獻面板）。<br/>**退組守恆**：退組時將在籍貢獻分沉澱至原組 `GroupProgress.historySummary`，隨後將本欄位重新錨定為當前 Col 5。 |

### 3.5 `MilestonesConfig`（篇章/寶箱/規則判定總表 — 10 欄 Col A ~ Col J）
* **直欄定義**：
  * `Col A (id)`：成就/篇章/任務唯一鍵（如 `CHP_01`~`CHP_08`, `CHEST_T1`~`CHEST_T6`）。
  * `Col B (title)`：成就名稱（如「美德篇」、「晨興守望者」）。
  * `Col C (targetType)`：判定對象（`PLAYER` 或 `GROUP`）。
  * `Col D (rewardPoints)`：獎勵點數（整數，無獎勵填 0）。
  * `Col E (repeatCycle)`：循環週期（`ONCE` 永久一次、`REPEAT`/`DAILY` 每日循環、`WEEKLY` 每週循環）。
  * `Col F (startDate)`：生效起始日（`YYYY-MM-DD` 或留空）。
  * `Col G (endDate)`：生效截止日（`YYYY-MM-DD` 或留空）。
  * `Col H (status)`：狀態（`ACTIVE` 啟用、`INACTIVE` 停用）。
  * `Col I (conditionType)`：判定條件函式代碼（支援以空格/AND 串接之複合條件）。
  * `Col J (parameters)`：JSON 格式參數字串（依 `conditionType` 要求配置）。
* **引擎判定與支援參數格式一覽**（完整演算規格請參見《10_成就與履約系統架構書.md》第 4.2 節）：

| 條件類型 (`conditionType`) | 適用對象 | 參數格式範例 (`parameters`) | 支援參數鍵名與說明 |
| :--- | :---: | :--- | :--- |
| `PLAYER_POINTS_THRESHOLD` | `PLAYER` | `{"threshold": 500}` | `threshold`: 個人總分達標門檻點數 |
| `GROUP_POINTS_THRESHOLD` | `GROUP` | `{"threshold": 5500}` | `threshold`: 小組總分達標門檻點數（八大篇章解鎖） |
| `GROUP_MEMBERS_COUNT` / `GROUP_MEMBER_THRESHOLD` | `GROUP` | `{"threshold": 2}` | `threshold`: 小組有效在籍人數門檻（CHP_01 建組） |
| `ALL_DAILY_PRACTICE` | `PLAYER` | `{}` | 可選 `{"targetDate": "YYYY-MM-DD"}`（預設目標結算日） |
| `DAILY_PRACTICE_STREAK` / `PRACTICE_STREAK` | `PLAYER` | `{"item": "morning", "streakDays": 7}` | `streakDays`: 連續天數；`item`: `'morning'`, `'bible'`, `'prayer'`, `'book'`, `'any'` |

### 3.9 進度帳本算分關聯與持久化寫入規範 (Progress Ledger Architecture & Formulas)

#### 3.9.1 核心算分關聯與能量守恆定理
依據 2026-10-14 重構架構（個人獎勵直接計入當年度結算分），系統徹底實現個人卓越追求與小組榮譽進程連動，其核心算分關聯如下：

1. **個人歷年總分 (`personalPoints`)**：
   $$\text{personalPoints} = \text{settledTotalScore (Col 5)} + \text{sumHistoryPoints}(\text{Player Col 2})$$
   * 由當前年度已結算總積分與往年封存歷史點數相加而成。
   * `ProgressLedger.sumHistoryPoints` 會自動忽略以底線 `_` 開頭之排程控制鍵（如 `_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`）。

2. **在籍小組貢獻分 (`contributionPoints`)**：
   $$\text{contributionPoints} = \max(0, \text{settledTotalScore (Col 5)} - \text{joinBaseScore (Col 6)})$$
   * 個人在組期間獲得的所有每日操練累計、個人里程碑點數、成就寶箱與個人特殊獎勵，皆直接累加至 Col 5，從而即時帶動個人對小組貢獻分等額成長。
   * **入組時間截斷防禦**：聖徒加入小組當下將 `joinBaseScore` 錨定為加入當下的 `settledTotalScore`，入組前之歷史得分不會回溯灌水給新小組（入組瞬間貢獻分嚴格為 0）。

3. **小組總積分 (`groupTotalPoints`)**：
   $$\text{groupTotalPoints} = \text{sumHistoryPoints}(\text{Group Col 2}) + \sum_{m \in \text{ActiveMembers}} \max(0, \text{Player Col 5}_m - \text{Player Col 6}_m)$$
   * 小組總分為「小組累積歷程分（歷年封存 + 離隊沉澱 + 小組篇章獎勵 + 管理員小組獎勵）」與「所有在籍組員在組期間之在籍貢獻分加總」。

4. **離隊退組能量守恆與二次截斷**：
   * 當組員調組或退出小組時，其在組期間之在籍貢獻分 $\max(0, \text{Col 5} - \text{Col 6})$ 全額固化沉澱入舊組 `GroupProgress.historySummary`（呼叫 `ProgressLedger.depositReward(ss, 'GROUP', oldGId, contrib)`）。舊小組總分完全守恆不倒退。
   * 退組當下，該聖徒之 `joinBaseScore` 立即重新錨定為當前 `settledTotalScore`（`newBaseScore = settledTotalScore`），使其在未入組期間或轉入新組時，貢獻分重新從 0 起算，杜絕向新組重複灌水或孤兒退組貢獻暴增。

#### 3.9.2 試算表實體寫入欄寬矩陣與物理隔離規範
持久化模組 `ProgressLedger` 在 Google Sheets 寫入時嚴格遵循矩陣欄寬隔離，絕不多寫或覆蓋保護欄位：

| 操作情境 | 目標工作表 | 寫入起始欄位 | 寫入欄寬 | 寫入涵蓋直欄代碼 | 物理隔離保護機制 |
| :--- | :--- | :---: | :---: | :--- | :--- |
| **個人獎勵發放 / 里程碑結算**<br/>(`depositReward` / `batchApplyMilestoneSettlements`) | `PlayerProgress` | **Col 2** (B) | **4** | Col B (`historySummary`)<br/>Col C (`milestones`)<br/>Col D (`updatedAt`)<br/>Col E (`settledTotalScore`) | ⚠️ **嚴格保護 Col 6 (`joinBaseScore`)**！寫入範圍固定為 4 欄（Col 2~5），入組基準分享有實體物理隔離，絕不受個人獎勵發放覆蓋。 |
| **小組獎勵發放 / 篇章解鎖**<br/>(`depositReward` / `batchApplyMilestoneSettlements`) | `GroupProgress` | **Col 2** (B) | **3** | Col B (`historySummary`)<br/>Col C (`milestones`)<br/>Col D (`updatedAt`) | 小組專屬 3 欄寫入，點數沉澱至 Col B，里程碑紀錄至 Col C。 |
| **每日排程批次點數結算**<br/>(`batchUpdateSettledScores`) | `PlayerProgress` | Col 2 & Col 5 | 1 + 1 | Col B (`historySummary` 控制標記)<br/>Col E (`settledTotalScore` 結算分) | 雙直欄單欄獨立批次回寫，完全不接觸 Col C, D, F。 |
| **入組 / 調組 / 退組基準分更新**<br/>(`syncGroupMembership`) | `PlayerProgress` | **Col 6** (F) | **1** | Col F (`joinBaseScore`) | 單元格直寫更新基準分，與 Col 2~5 物理隔離。 |

> [!IMPORTANT]
> **Col 6 (`joinBaseScore`) 物理隔離原則**：
> `ProgressLedger` 在發放個人獎勵與結算里程碑時，寫入範圍嚴格限定為 `getRange(row, 2, 1, 4)`（Col 2~5），杜絕任何對 Col 6 的盲目覆寫，確保入組截斷基準分的權威性與不變性。同時，在記憶體中同步更新 `pInfo.settledTotalScore`，消除持久化層與記憶體字典狀態不一致的潛在隱患（Zero Drift）。

## 5. Base-100 數值打包編碼與加總定理

### 5.1 每日操練公式 (DailyMatrix)
$$\text{PackedValue} = (\text{book} \times 10^6) + (\text{prayer} \times 10^4) + (\text{bible} \times 10^2) + \text{morning}$$
* **全勤數值**：$1 \times 10^6 + 1 \times 10^4 + 1 \times 10^2 + 1 = 1010101$。

### 5.2 每週聚會公式 (MeetingMatrix)
$$\text{PackedValue} = (\text{outreach} \times 10^6) + (\text{lordDay} \times 10^4) + (\text{prayerMtg} \times 10^2) + \text{group}$$
* **全勤數值**：$1010101$。

### 5.3 十進位加總定理 (Sum-Decode Theorem)
在 $\le 99$ 天或 $\le 99$ 週的範圍內，各項目次數累計絕不產生進位干擾：
* 晨興/小排次數：$\text{Sum} \pmod{100}$
* 讀經/禱會次數：$\lfloor (\text{Sum} \pmod{10000}) / 100 \rfloor$
* 禱告/主日次數：$\lfloor (\text{Sum} \pmod{1000000}) / 10000 \rfloor$
* 書報/探訪次數：$\lfloor \text{Sum} / 1000000 \rfloor \pmod{100}$

後端呼叫試算表原生 `SUM()` 函式即可在微秒內完成單一成員長週期統計，零迴圈遍歷。
