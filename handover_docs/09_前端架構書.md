# 🖥️ 文檔七：前端架構書

> **目的**：原生 JavaScript Mobile-First PWA SPA 的分層架構、狀態庫演算法、通知體系、無障礙規範與視圖元件。

---

## 1. 前端技術架構

* **無框架原生 SPA 設計**：使用原生 DOM API (ES6+)，零框架相依性，低維護門檻，追求極致載入效能與記憶體純淨。
* **部署形式**：GitHub Pages 靜態託管（雙軌倉庫：`origin` 測試站 / `khya` 正式站）。
* **Service Worker (`sw.js`)**：靜態圖資採 Cache-First，業務邏輯採 Network-First，支援 PWA 離線容錯與背景更新（目前快取版本：`vital-cache-v105` / `v105`，靜態資產版本戳記：`20261015-v105`）。

## 2. 前端目錄與模組分層

* **控制器層 (`src/frontend/html/js/app.js`)**：協同全站生命週期、事件分發、彈窗滾動鎖定、前景喚醒時鐘校準。
* **通訊層 (`src/frontend/html/js/api/apiClient.js`)**：
  * **Iframe RPC 跨域橋接**：透過隱藏 Iframe (`Bridge.html`) 與 `postMessage` 雙向通訊，徹底解決 Google Apps Script 在 Safari / iOS 隱私模式下的第三方 Cookie 阻擋與跨域重定向問題。
  * **三微服務動態分發**：依照 Action 路由表自動分派至 Core (`execCoreAction`), Progression (`execProgressionAction`), Chat (`execChatAction`)。
  * **在途互斥鎖 (In-Flight Mutex)**：相同簽名的並發請求自動合併排隊，避免重複扣點或重複發送。
  * **雙軌網關切換**：自動適配 `origin` (測試站) 與 `khya` (正式上線站) 後端 Web App URL。
* **狀態庫層 (`src/frontend/html/js/store/`)**：
  * `practiceStore.js`：10ms 樂觀更新、隊列收斂 (Latest-Wins)、細粒度欄位突變追蹤、琥珀點 (未同步) 標記、離線回播。
  * `chatStore.js`：Cache-First 秒開、45s 智慧輪詢、焦點感知、發言互斥鎖 (3,000ms 逾時熔斷)。
* **純領域引擎層 (`src/frontend/html/js/modules/`)**：
  * `journeyEngine.js`：篇章推進百分比與 Gap 試算（純函式，無 DOM 操作；相容推導小組累積總分 `groupTotalPoints` / `journeyPoints`，包含組員貢獻分與小組歷史獎勵）。
  * `pendingPointsEngine.js`：待結算點數試算（正式分與在途分徹底解耦；依據今日打卡與本週聚會狀態試算未結算點數，已固化項目 `solidifiedItems` 嚴格排除計分）。
  * `storageGateway.js`：Web Storage 雙態儲存閘道、登出雙階清除 (Dual-Phase Purge)。
  * `userSessionCoordinator.js`：5 態會話狀態機 (`UNAUTHENTICATED` ➔ `HYDRATING` ➔ `SYNCHRONIZING` ➔ `ACTIVE` ➔ `EXPIRED`)。
* **視圖層 (`src/frontend/html/js/ui/`)**：包含 `authView.js`, `dashboardView.js`, `chestView.js`, `footprintsView.js`, `groupFellowshipView.js`, `profileView.js`。
* **工具層 (`src/frontend/html/js/utils/`)**：
  * `vitalUtils.js`：`VitalToast` 輕量通知引擎、XSS 實體轉義、日期字串標準化。
  * `avatarManager.js`：頭像滑動視窗預載、環形越界處理。

## 3. 核心狀態庫演算法與狀態管理

### 3.1 `OptimisticPracticeStore` 細粒度欄位突變追蹤與權威同步演算法
為徹底根除打卡撤回時因單調布林 OR 聯集（`cur || server || pending`）造成的「幽靈復活 (Ghost Resurrection)」缺陷，實作細粒度欄位追蹤：

1. **細粒度欄位突變追蹤 (Field Mutations)**：
   * 建構子初始化 `dailyMutations` (Map of Sets) 與 `meetingMutations` (Map of Sets)。
   * 當使用者點擊 `toggleDailyPractice` 或 `toggleMeetingPractice` 時，精確將被主動變更之特定欄位名加入對應日期的 Set 中。
2. **在途與隊列保護 (Latest-Wins)**：
   * 在 `mergeServerPractice` 中，針對該欄位進行細粒度判定：若該欄位正處於本地未同步狀態（在途發送或收斂佇列中），嚴格以本地最新意圖為準，絕不被過期的伺服器快照覆蓋。
3. **權威狀態同步與反向取消**：
   * 若該項目本地未曾變更，或變更已由伺服器成功確認（`syncStatus = 'synced'` 且清空突變記錄），則權威對齊伺服器真實狀態，支援反向取消（Uncheck）並同步跨裝置打卡。
4. **聚會固化不變量守恆 (Solidification Invariant)**：
   * 若聚會項目已存在於 `solidifiedItems` 中，強制為 `true`，鎖定不可退轉，前端攔截反選操作並回傳提示。

### 3.2 保持登入雙態儲存與登出雙階掃除 (Dual-Storage & Dual-Phase Purge)
* **雙態儲存架構**：依據登入頁 `#keepLoginCheckbox` 勾選狀態：
  * **勾選保持登入**：Token 與個人資料持久化至 `localStorage`，重新開啟瀏覽器分頁自動無感水合。
  * **未勾選**：僅暫存於 `sessionStorage`，關閉分頁或新分頁立即銷毀會話，徹底杜絕公用電腦上的隱私外洩風險。
* **5 態會話狀態機 (`UserSessionCoordinator`)**：
  * `UNAUTHENTICATED`：未驗證，阻擋需要授權之視圖。
  * `HYDRATING`：正在讀取本地 Storage 水合使用者資料。
  * `SYNCHRONIZING`：背景發起請求向 GAS 對齊最新狀態。
  * `ACTIVE`：會話有效且狀態已同步。
  * `EXPIRED`：會話逾期或遭遇 401/403，安全退回未登入狀態。
* **原子登出雙階掃除 (Dual-Phase Purge - `StorageGateway`)**：
  * **Phase 1（標靶清除）**：精確清除當前使用者的 Token、身分物件、在途離線隊列 (`vital_offline_queue`) 以及個人快取 (`vital_daily_records_${playerId}`, `vital_chat_cache_${groupId}` 等)。
  * **Phase 2（全域掃描白名單保護）**：遍歷所有 `vital_` 前綴鍵值，除白名單保護項目（篇章/點數/成就/任務/里程碑等靜態設定、快取日期、記憶登入偏好）外，徹底刪除所有私有用戶殘留，杜絕多帳號切換時的離線串供或幽靈數據。

### 3.3 點數流向、權威水合與個人獎勵重構整合現狀
* **純後端重構與前端 100% 零修改**：
  * 本次【個人獎勵點數改計入當年度結算分 (`settledTotalScore`) 並連動小組貢獻】為純後端領域與持久化層重構。
  * 後端微服務 API 端點契約（`getProgressBundle`, `getPlayerProgress`, `getGroupProgress`, `getGroupJourney` 等）回傳之 JSON 資料結構與欄位名稱保持 100% 向後相容，前端無須改動任何程式碼。
* **權威水合機制 (Store & Profile Hydration)**：
  * 前端在 `app.js` 透過 `bundlePromise`（呼叫 `apiClient.getProgressBundle`）與 `refreshUserData` 接收後端 Progression 模組回傳之資料，直接水合至 `currentUserProfile` 與本地快取：
    * `personalPoints`：直接讀取後端結算總分（`settledTotalScore + Σ historySummary`），已自動累加包含個人里程碑與個人特殊獎勵在內的所有個人點數；映射至首頁英雄卡下半部 `#homePersonalScoreText` 及個人資料頁 `#myPersonalPoints`。
    * `contributionPoints`：直接讀取後端計算之在籍貢獻分（$\max(0, \text{settledTotalScore} - \text{joinBaseScore})$，未入組為 0），組員在組期間獲得個人獎勵時，貢獻分即時自動成長；映射至同行貢獻彈窗、個人資料頁 `#myContributionPoints` 與首頁相容隱藏節點 `#homeContributionText`。
    * `groupTotalPoints`：直接讀取小組總分（小組歷史沉澱分 + 所有在籍組員 `contributionPoints` 加總），自動反映在籍成員之個人卓越成果；映射至首頁英雄卡上半部 `#homeGroupScoreText`。
* **正式分數與未結算在途分徹底解耦 (Zero Pseudo-Settlement)**：
  * 前端各視圖顯示之正式分數直接反映已結算權威值，不再於本機樂觀疊加臨時加分（消除本地偽結算導致的跨裝置數值漂移與幽靈點數）。
  * 今日每日操練與本週聚會打卡，由純領域引擎 `pendingPointsEngine.js` 獨立試算為「待結算點數膠囊」（Pending Chips），明確告知使用者將於明日凌晨結算入帳。
* **聚會固化防禦與狀態庫閉環**：
  * 每日增量結算完成後，後端透過 `solidifiedItems` 下發已結算聚會清單。
  * 狀態庫 `practiceStore.js` 觸發固化鎖定（`isSolidified: true`），攔截反選撤回，UI 觸發發光金邊（`.quest-card.is-solidified`）與雙 Toast 交互（見 4.1 與 5.1）。

## 4. 全域通知與互動安全規範

### 4.1 `VitalToast` 輕量化通知系統
* **架構定位**：全域統一非阻塞提示引擎（掛載於 `VitalUtils.VitalToast`），全面淘汰瀏覽器原生阻塞式 `alert()`（全前端 100% 零原生 alert 殘留）。
* **規格與特徵**：
  * **三段位置支援**：`pos-top`（頂部）、`pos-center`（中央）、`pos-bottom`（底部，默認）。
  * **四色主題規範**：
    * `toast-info`：深石灰 `#1e293b`（一般提示、離組提醒）
    * `toast-gold`：尊榮暖金 `#f59e0b`（里程碑達成、建立活力組、金邊固化鎖定）
    * `toast-success`：翡翠薄荷綠 `#0d9488`（儲存成功、加入小組、隊長移交）
    * `toast-error`：柔和珊瑚紅 `#dc2626`（表單驗證錯誤、未登入攔截、密碼不符）
  * **內建提示整併與雙 Toast 交互機制**：
    * **新打卡待結算提示 (`showMeetingPendingToast_`)**：點擊每週聚會卡片完成打卡時，彈出 `toast-info`（底部，10s），提示「🕊️ 已記錄聚會打卡！將於明日凌晨 03:00 結算入帳，【今日內可隨時點擊撤回】。」；若當日內再次點擊取消打卡，則調用 `dismissToast_()` 自動撤回提示。
    * **固化鎖定防禦提示 (`showSolidifiedNoticeToast_`)**：若點擊已存在於 `solidifiedItems` 清單中之項目，狀態庫強制阻斷撤回，彈出 `toast-gold`（中央，2.5s），提示「✨ 此聚會已於昨日完成結算入帳，不可取消打卡囉！」。

### 4.2 全站彈窗無障礙 (a11y) 與互動規範
* **無障礙標籤配置**：全站所有 Modal 容器強制宣告 `role="dialog"`, `aria-modal="true"`，並為各彈窗標題配置唯一 ID 與 `aria-labelledby`。
* **關閉按鈕標準熱區**：所有 `.modal-close-btn` 強制宣告 `aria-label="關閉"`，並在 CSS 宣告最小 44px 觸控熱區 (`min-width: 44px; min-height: 44px;`)，符合行動裝置無障礙點擊規範。
* **遮罩背景點擊安全關閉 (Click-Outside Dismissal)**：
  * 在 `app.js` 全域點擊監聽器中實作遮罩判定：當點擊事件目標為 `.modal-layer` 本身（排除內部 `.modal-card` 卡片本體）時，自動將該彈窗標記 `hidden` 關閉。
  * **架構決策**：不綁定鍵盤 Escape 鍵（維持行動裝置觸控與點擊行為單純）。
* **背景穿透滾動防護 (Background Scroll Bleed Prevention)**：
  * 彈窗開啟時由 `MutationObserver` 自動為 `body` 添加 `.modal-open` 樣式 (`overflow: hidden !important; touch-action: none;`)。
  * 在 `.modal-layer` 與 `.modal-card` 宣告 `overscroll-behavior: contain;`，物理隔絕滾動鏈穿透。

### 4.3 通用彈窗防非同步競態機制 (`InfoModalGuard`)
* **架構背景與解決痛點**：
  * `#infoModal` 是全系統唯一的「多用途通用彈窗」，由 6 大業務視圖共用（同行貢獻 `contribution`、同行足跡 `footprints`、全召會旅程榜 `journey_list`、系統公告 `announcements`、個人成就寶箱 `chest_list`、需要活力組操練鎖定提示 `group_required`）。
  * 過去當使用者開啟「同行貢獻」觸發背景非同步資料抓取，若在網路尚未回傳前關閉並點開「同行足跡」，延遲抵達的 Promise 回呼會無條件將資料寫入 `#infoModalContent`，導致彈窗標題仍為「同行足跡」而內容卻被覆蓋為「同行貢獻」之嚴重競態問題。
* **會話管理與三重防禦門檻 (`VitalUtils.InfoModalGuard`)**：
  1. **所有權宣告 (Claim Ownership)**：
     * 呼叫 `claim(modalType)` 時自動將全域會話序號計數器遞增 (`sessionId = ++_infoModalSessionCounter`)。
     * 同步在 `#infoModal` DOM 節點掛載 `dataset.activeModalType` 與 `dataset.modalSessionId`，並回傳 `{ sessionId, modalType, isCurrent(), invalidate() }` 控制句柄。
  2. **三重寫入防禦門檻 (`isActive(modalType, sessionId)`)**：
     * **門檻 1 (可見性)**：彈窗必須處於非隱藏狀態（`!modal.classList.contains('hidden')`），彈窗關閉後任何延遲回傳嚴禁喚醒或污染 DOM。
     * **門檻 2 (類型一致性)**：當前彈窗宣告之 `activeModalType` 必須與回呼持有之 `modalType` 嚴格相等，防止遭後續開啟之其他視圖搶佔後被覆蓋。
     * **門檻 3 (會話序號匹配)**：當前 DOM 的 `modalSessionId` 必須與發起時取得之 `sessionId` 嚴格相等，防止同一視圖重複發起時舊請求覆寫新請求。
  3. **及時會話作廢 (Invalidation)**：
     * 當使用者點擊關閉按鈕（`[data-close-modal="infoModal"]`）或遮罩背景（Click-Outside）時，自動調用 `InfoModalGuard.invalidate()` 將當前彈窗類型清空並重置 session ID 為 `0`，立即使所有在途非同步請求的回呼失去寫入權限。
* **6 大呼叫點全面防禦**：
  * **非同步資料載入者 (SWR & Async)**：
    1. `profileView.openContributionModal()`：宣告 `'contribution'`，在 SWR 快取覆寫、`Promise.allSettled` 返回與錯誤呈現前皆以 `guard.isCurrent()` 阻斷。
    2. `footprintsView.openFootprintsModal()`：宣告 `'footprints'`，在快取渲染、骨架屏、後端 API 回傳、SWR `revalidatePromise` 與錯誤處理皆以 `guard.isCurrent()` 與 DOM activeModalType 雙重防禦。
    3. `dashboardView.openGroupJourneyListModal()`：宣告 `'journey_list'`，在 API 回傳與錯誤處理前嚴格校驗 `guard.isCurrent()`。
  * **同步搶佔保護者**：
    4. `dashboardView.openAnnouncementsModal_()`：開啟前宣告 `'announcements'`，立即使前一個在途非同步請求失效。
    5. `chestView.openChestModal()`：開啟前宣告 `'chest_list'`，立即使前一個在途非同步請求失效。
    6. `dashboardView.openGroupPracticeRequiredModal()`：開啟前宣告 `'group_required'`，立即使前一個在途非同步請求失效。
* **專項測試保障**：
  * 新增專項單元測試 `tests/unit/modalRaceCondition.test.js`，模擬「貢獻➔足跡」、「足跡➔貢獻 SWR」、「開啟➔關閉」、「非同步➔寶箱/公告」等極端競態場景，全數 100% 綠燈通過。

## 5. 渲染效能與動效規範

### 5.1 GPU 合成層動效規範
* **發光光暈最佳化**：每週聚會卡片金邊發光動效（`.quest-card.is-solidified`）嚴禁動態變更 `box-shadow` 的模糊半徑（防止引起 CPU 逐幀 Repaint 重繪發熱）。
* **合成層動態**：透過 `::after` 獨立偽元素圖層配置固定光暈，使用 GPU 原生加速的 `opacity: 0.25` $\to$ `opacity: 0.85` 驅動 `@keyframes goldGlowPulse` 呼吸循環，並宣告 `will-change: opacity`，保證 120fps 極致滑順且節能。

### 5.2 靜態資產閒置預載
* `avatarManager.js`：利用環形雙重餘數演算法，在切換頭像時預載周圍 $x-2, x-1, x+1, x+2$ 圖片。
* `chestView.js`：在建構式中自動利用 `requestIdleCallback` / `setTimeout` 非同步預載 10 階寶箱 WebP 資產，消除彈窗白屏延遲。

## 6. 視圖重點功能與跨夜時鐘自癒

* **儀表板首頁 (`DashboardView`)**：跑馬燈公告、篇章橫向抓取拖曳軌道 (Grab-to-scroll)、今日操練卡（晨興、讀經、禱告、書報）與每週聚會卡（相調探訪、小排、禱告聚會、主日）。
  * **首頁點數面板改版規格 (`.hero-score-grid`)**：
    * **上半部：小組整組累積總點數（卡片 1：`.hero-score-card.hero-group-score`）**：
      * **標籤與 DOM ID 定義**：標籤 `<span>小組</span>`、數值 `<strong id="homeGroupScoreText">---</strong>`、單位 `<small id="homeGroupScoreUnit" hidden>點</small>`、同步狀態 `<em id="homeGroupSyncText" class="score-sync-badge" hidden></em>`。
