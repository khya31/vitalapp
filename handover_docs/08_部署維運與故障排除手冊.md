# 文檔八：部署、維運與故障排除手冊

> **目的**：讓接手者能獨立完成 GAS 後端手動部署、雙軌 Git 發布、定時排程配置以及線上突發故障的應急排除。

---

## 1. 權限與憑證配置

- **Google 帳號**：需具備 Core、Chat、Progression 三核心試算表之「編輯者」權限。特別注意：設定 Progression 定時排程的帳號，必須同時對 Core 試算表具備讀取權限，首次手動執行需完成 OAuth 授權視窗確認。
- **試算表 ID 配置**：Progression 與 Chat 專案中之試算表 ID 為代碼常數寫死；Core 專案支援自 `ScriptProperties` 讀取並以代碼常數作為 Fallback。
- **前端 `runtime-settings.js` 網址對照**：
  - 定義三大微服務的正式 Web App URL。發布前需確保網址正確指向目標環境。

## 2. 後端部署 SOP（手動貼上）

三大微服務為試算表容器綁定專案 (Container-bound Scripts)，目前採手動貼上發布更新：

1. **Core 服務**：複製 `dist/core/Code.gs` 與 `dist/core/Bridge.html`，貼入【核心業務試算表】之 Apps Script 專案。
2. **Chat 服務**：複製 `dist/chat/Code.gs` 與 `dist/chat/Bridge.html`，貼入【小組交流試算表】之 Apps Script 專案。
3. **Progression 服務**：複製 `dist/progression/Code.gs` 與 `dist/progression/Bridge.html`，貼入【成就履約試算表】之 Apps Script 專案。
4. **GAS 檔案建立與設定必讀**：
   - ⚠️ **HTML 檔案建立**：建立 `Bridge` 時，必須在左側點擊「**新增檔案 (+) ➔ HTML**」並命名為 `Bridge`（嚴禁建為 `.gs` 指令碼，否則全站通訊將因找不到檔案而癱瘓）。
   - 點擊「部署」 ➔ 「管理部署作業」 ➔ 點擊鉛筆「編輯」 ➔ 選擇「**新版本**」 ➔ 「儲存」。
   - **執行身分 (Execute as)**：必須為「**我 (Me - 擁有者)**」。
   - **誰可以存取 (Who has access)**：必須為「**所有人 (Anyone)**」。
   - ⚠️ **高壓線**：嚴禁點擊「新增部署作業」，否則會生成新的 Web App URL，造成線上所有前端請求失效。
5. **健康檢查探針**：瀏覽器造訪 `https://<webAppUrl>/exec?format=json`，確認回傳 `{"status": "ONLINE", "version": "2.0.0"}`。

## 3. 前端雙軌發布 SOP（特別說明）

### 3.1 雙遠端用途明確定義
* **`origin` (hsnu125739/vitalapp)**：**測試專案**，供工程師驗證新功能與快取更新。網址：`https://hsnu125739.github.io/vitalapp/`
* **`khya` (khya31/vitalapp)**：**正式對外上線專案**，供全召會聖徒正式使用。網址：`https://khya31.github.io/vitalapp/`

### 3.2 快取版本升級指南（Cache Busting Guide：v104 ➔ v105 實例）
為了防止 PWA Service Worker 與瀏覽器 HTTP Cache 咬住舊版靜態資源，任何前端 UI、樣式或業務邏輯更動時，**必須執行雙軌快取版本同步遞增**：
1. **Service Worker 快取名稱 (`sw.js`)**：
   - 開啟 `src/frontend/html/sw.js`，修改頂部的 `CACHE_NAME` 常數。
   - **版本進程**：例如由 `vital-cache-v104` 遞增為 **`vital-cache-v105`**。
   - 作用：驅使瀏覽器觸發 Service Worker 的 `install` 與 `activate` 生命週期，自動清除舊版快取並緩存新檔案。
2. **靜態資源查詢字串 (`index.html`)**：
   - 開啟 `src/frontend/html/index.html`，同步替換所有 `<link rel="stylesheet">` 與 `<script src="...">` 標籤的查詢參數 `?v=...`。
   - **版本進程**：例如由 `?v=20261014-v104` 遞增為 **`?v=20261015-v105`**。
   - 作用：確保瀏覽器直接透過網路載入新檔案，避免在 SW 接管前被 HTTP 磁碟快取咬死。
3. **改版驗證依歸（以 v105 通用彈窗防競態 InfoModalGuard 為例）**：
   - **功能變更**：
     - 通用多目的彈窗 `#infoModal` 會話所有權與作用域守衛（`InfoModalGuard`），杜絕同行貢獻、同行足跡、全召會旅程榜、系統公告、成就寶箱與操練未解鎖提示等 6 處共用彈窗之非同步覆蓋與標題/內容不一致競態缺陷。
     - 具備 3 大驗證閘門（可見性門檻、視圖型別門檻、會話序號新鮮度）與關閉即時註銷機制。
   - **測試門禁**：包含新增之 `tests/unit/modalRaceCondition.test.js` 與 Condition Engine 屬性檢驗專項，全系統測試基準達 625/625 PASS，方可發布並鎖定版本為 `v105`。

### 3.3 雙遠端發布標準步驟
> ⚠️ **工作目錄警告**：專案根目錄非 Git 倉庫，必須切換至 `src/frontend/` 執行！

1. **前置測試驗證**：
   在專案根目錄下執行基準測試，確認 625/625 PASS 無迴歸：
   ```bash
   agy-node tests/run-all.js
   ```
2. **同步遞增快取版本**：
   依上述 3.2 節指南，將 `src/frontend/html/sw.js` 遞增至 `vital-cache-v105`，並更新 `src/frontend/html/index.html` 之 `?v=20261015-v105`。
3. **切換至 Git 倉庫**：
   ```bash
   cd src/frontend
   ```
4. **測試發布與驗收 (Deploy to Test - origin)**：
   ```bash
   git add .
   git commit -m "fix(modal): 實作 InfoModalGuard 防護共用彈窗非同步競態覆蓋缺陷 (v105)"
   git push origin main
   ```
   推送完成後，造訪 `https://hsnu125739.github.io/vitalapp/`，以測試帳號驗收新功能與快取更新。
5. **正式上線發布 (Deploy to Production - khya)**：
   測試站驗收通過後，推送至正式對外專案：
   ```bash
   git push khya main
   ```
   造訪 `https://khya31.github.io/vitalapp/`，確認正式站上線無誤。
6. **環境清理與返回根目錄**：
   ```bash
   cd ../..
   ```

## 4. 定時排程與維運

### 4.1 夜間凌晨結算排程 (Daily Settlement Trigger)
- **排程觸發設定**：
  - 專案：成就履約 (Progression) 專案。
  - 觸發函式：`runDailyMilestoneSettlement`（Time-driven Trigger）。
  - 執行頻率：每日定時器（日計時器）。
  - 時段設定：**每日凌晨 03:00 至 04:00**（配合每日凌晨 03:00 打卡截止固化點）。
  - 警報設定：GAS 觸發條件介面設定「失敗通知頻率：立即通知」。
- **核心執行管線 (Execution Pipeline)**：
  函式直連進入 `SettlementCoordinator.executeDailySettlement`，依序完成兩階段核心工作流：
  1. **操練與聚會增量差集結算**：
     - 委託 `SettlementEngine.calculateMemberDelta` 計算昨日操練與本週聚會增量差集（昨日聚會打卡、今日凌晨立即結算入帳）。
     - 批次更新 `PlayerProgress` 之 Col 2（`historySummary` 寫入控制戳記 `_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`）與 Col 5（`settledTotalScore` 累加增量分）。
  2. **批次里程碑與篇章連動評估 (`runBatchMilestoneSettlement`)**：
     - 委託 `MilestoneCoordinator.runBatchMilestoneSettlement` 評估個人里程碑、成就寶箱與特殊任務。
     - **同晚小組篇章即時連動機制**：當組員在當晚達成個人成就獲獎時，該獎勵點數即時同步至 `pRowInfo.settledTotalScore` 並原子累加至小組即時總分快照 `groupScoreMap[pGid]`，使緊接著在下方執行的小組篇章評估能即時感知包含個人獎勵的新總分，實現「同晚個人獲獎、同晚突破門檻解鎖小組篇章（跨篇章解鎖）」。
  3. **矩陣批次持久化落盤**：
     - 委託 `ProgressLedger.batchApplyMilestoneSettlements`，一次性矩陣寫入 `PlayerProgress`（Col 2~5，第 6 欄 `joinBaseScore` 物理隔離）、`GroupProgress`（Col 2~4）與 `TaskClaims`（達成憑證）。
  4. **小組旅程快取清理**：
     - 排程執行完畢前自動清除 Script Cache Key：`vital_group_journey_list`，保證前端旅程地圖與 API 即時取得最新小組篇章進度。

### 4.2 歷史資料遷移紀錄與維護規範 (歷史個人獎勵遷移已結案)
- **歷史個人獎勵遷移執行紀錄**：
  - **背景**：系統先前架構將個人獎勵點數寫入 `PlayerProgress` Col 2 的 `historySummary["2026"]`，導致個人獎勵未能進入 Col 5 `settledTotalScore`，無法帶動個人小組貢獻分。
  - **執行完成**：2026 年度歷史個人獎勵遷移（一次性函式 `runMigratePlayer2026Rewards()`）已於 **2026-10-14** 順利執行完畢。全體聖徒歷史個人獎勵點數已全數落盤至 Col 5 (`settledTotalScore`)，Col 2 的 `"2026"` 鍵已徹底清除，往年封存分數（`"2024"`, `"2025"`）與排程系統戳記（`_lastSettledDate` 等）100% 完好保留。
- ⚠️ **過渡代碼清理與維運禁令**：
  - 遷移過渡函式 `runMigratePlayer2026Rewards()` 與 `migrateLegacyPlayer2026Rewards_()` 已經依 `/ponytail` 極簡主義規範自 `dist/progression/Code.gs` 中徹底清理刪除。
  - **維運高壓線**：所有歷史點數已全數平移落盤，維運人員**無需、也嚴禁再次手動建立或執行任何歷史個人獎勵遷移函式**，避免破壞帳本守恆造成點數重複累加。
- **現行個人獎勵入帳常態**：
  - 目前所有個人獎勵（個人里程碑、成就寶箱、特殊任務、管理員個人發放之同行獎勵）在領域層與持久化層皆原生直入 Col 5 (`settledTotalScore`)，並透過 Col 6 (`joinBaseScore`) 實現入組前截斷與退組沉澱，日常維運無需任何手動介入。

## 5. 故障排除 Runbook (SOP)

### 5.1 GAS 執行逾時 (6分鐘)
- **排查**：多日斷層補算積累過多天數，或違背了 Bounding-Box 原則（在迴圈內呼叫 `getRange`）。
- **應急解法**：手動分批補算，或檢視執行記錄確認是否為全表掃描過慢。

### 5.2 聖徒回報打卡未儲存
- **排查**：處於弱網離線佇列中。
- **解法**：請聖徒確認網路良好後重新整理 App，前端 `OptimisticPracticeStore` 具備自動重試與 Replay 機制，在連線恢復時自動將琥珀未同步資料補送。

### 5.3 跨午夜結算遺漏與超長斷層 (>7天) 補算
- **排查**：排程觸發器漏跑或授權過期。
- **7天內斷層**：手動至 Progression 專案點擊「執行」`runDailyMilestoneSettlement`，系統會自動追溯最多 7 天之操練。
- **超長斷層 (>7天) 死鎖應急解法**：
  因 `resolveCatchupDates` 上限為 7 天，相差 >7 天時會引發 `isNextDay` 斷裂而無法自動前進。請在 Progression 專案中新增以下臨時函式分批手動推進：
  ```javascript
  function emergencyManualCatchup() {
    // 依序由遠及近推進日期，第二參數傳 true 強制結算聚會
    runDailyMilestoneSettlement('2026-10-05', true);
    runDailyMilestoneSettlement('2026-10-06', true);
    runDailyMilestoneSettlement('2026-10-07', true);
  }
  ```
  手動補算完成後，系統會自動清理 `vital_group_journey_list` 快取；亦可手動執行 `clearProgressionConfigCache()` 確保旅程快取全面刷新。

### 5.4 前端發布後畫面未更新與 GitHub Pages 故障排除
前端靜態託管於 GitHub Pages 並透過 PWA Service Worker 進行資源快取。若發布後聖徒反映畫面仍為舊版，依序進行以下三個層級的排查：

#### 5.4.1 GitHub Pages 部署延遲或未觸發建置 (Pages Deployment Failure/Lag)
- **排查**：
  - 推送到 `origin` 或 `khya` 後，至對應 GitHub 倉庫查看 `Settings ➔ Pages` 或 `Actions` 頁籤中的部署紀錄。
  - 若 GitHub Pages 建置隊列卡住、逾時或未被 webhook 自動觸發，網站可能長時間維持舊版本。
- **解法（空提交強制觸發建置）**：
  在 `src/frontend/` 目錄建立空提交，強制觸發 GitHub Pages 重新建置管線：
  ```bash
  cd src/frontend
  git commit --allow-empty -m "chore: trigger pages deployment"
  git push origin main    # 或 git push khya main
  cd ../..
  ```
  約等候 1~2 分鐘後重新檢查 Actions/Pages 狀態至綠色完成。

#### 5.4.2 瀏覽器 HTTP 快取與 Service Worker 咬死舊版
- **排查**：
  1. 檢查 `sw.js` 之 `CACHE_NAME` 是否已確實自舊版（例如 `v103`）遞增至新版（目前基準為 **`vital-cache-v104`**）。
  2. 檢查 `index.html` 之所有 `<script>` 與 `<link>` 查詢字串是否皆已更新為 **`?v=20261014-v104`**。
- **客戶端強制重整與清除指引**：
  - **桌面瀏覽器 (Chrome / Edge / Safari)**：
    - 按下 `Ctrl + F5` (Windows) 或 `Cmd + Shift + R` (Mac) 執行硬性重新整理。
    - 或開啟開發者工具 (F12) ➔ `Application` ➔ `Service Workers` ➔ 點擊 `Update` 或 `Unregister`。
  - **手機 PWA / 捷徑 App (iOS Safari)**：
    - 將已安裝至主畫面的 Web App 向上滑動徹底關閉進程，重新點擊進入。
    - 若仍殘留，開啟「設定 ➔ Safari ➔ 進階 ➔ 網站資料」，搜尋並刪除 `github.io` 快取資料。
  - **手機 PWA / 捷徑 App (Android Chrome)**：
    - 在 Chrome 瀏覽器造訪該網址，點擊網址列左側圖示 ➔ 「網站設定」 ➔ 「清除資料與重設」。

#### 5.4.3 雙遠端部署不一致排查 (Dual-Remote Drift)
- **排查情境**：工程師在測試站 (`origin`) 驗收完成後，遺漏了推送至正式站 (`khya`)，導致全體聖徒反映未見更新。
- **驗證與修復指令**：
  ```bash
  cd src/frontend
  git fetch origin
  git fetch khya
  git log origin/main -n 1 --oneline
  git log khya/main -n 1 --oneline
  ```
  若 `khya/main` 的 commit hash 落後於 `origin/main`，立即補推：
  ```bash
  git push khya main
  cd ../..
  ```

### 5.5 小組總分、個人貢獻或旅程篇章未即時更新排查
- **排查情境**：組員獲獎或深夜排程結束後，前端小組旅程畫面未顯示最新解鎖篇章，或首頁小組總點數未即時更新。
- **可能原因**：
  1. 後端 Script Cache 中的 `vital_group_journey_list` 快取尚未過期或殘留。
  2. 前端本機快取尚未同步。
- **應急解法與驗證步驟**：
  1. **手動清除後端快取**：後端夜間排程與小組成員變更作業均會自動清除 `vital_group_journey_list`。若遇突發快取咬死，管理員可開啟 Progression 專案，手動執行 `clearProgressionConfigCache()` 函式，即可一鍵清除包含 `vital_group_journey_list` 在內的所有設定與旅程快取。
  2. **驗證進度帳本欄位與點數守恆公式**：
     - 開啟【成就履約試算表】的 `PlayerProgress` 工作表，檢查：
       - Col 5 (`settledTotalScore`)：個人當年度結算總分（包含操練、聚會與個人里程碑/獎勵）。
       - Col 6 (`joinBaseScore`)：入組基準分（加入小組當下的個人總分，嚴禁為空或 0）。
     - 確認個人對小組貢獻分符合：
       $$\text{contributionPoints} = \max(0, \text{settledTotalScore} - \text{joinBaseScore})$$
     - 確認小組總分符合點數守恆公式：
       $$\text{groupTotalPoints} = \sum \text{historySummary(Group Col 2)} + \sum_{m \in \text{ActiveMembers}} \text{contributionPoints}_m$$
     - 若組員曾離隊，確認其在籍期間累積之貢獻分已沉澱至原組 `GroupProgress` Col 2 `historySummary`。
  3. **首頁點數面板改版（v104）對照查驗**：
     - **上半部（小組整組累積總點數）**：
       - 數據來源為 `groupTotalPoints`。
       - 若聖徒尚未加入任何活力組（`groupId` 為空），數值顯示 `"---"` 且單位「點」自動隱藏。
       - 若聖徒已加入活力組，顯示小組總分與單位「點」。
     - **下半部（個人整年累積總點數）**：
       - 數據來源為個人年度結算總分 `settledTotalScore`。
     - **彈窗互動**：
       - 點擊上半部或下半部卡片，皆統一呼叫 `openContributionModal` 打開「同行貢獻面板」，顯示同行組員個人總分、入組基準分與實質貢獻分清單。
     - **色彩與樣式契約**：
       - 上半部桃紅 `#d66b91`、下半部青綠 `#2f8f7e`，數字字級嚴格鎖定 `28px`，禁止偏離規範。
