## 2. O(1) 權威結算分數架構

* **2.1 個人總分**：`personalPoints = settledTotalScore + Σ historySummary`
  * **當年度收斂於 Col 5**：當年度每日操練、每週聚會結算分，以及所有**個人成就／里程碑／特殊獎勵點數**，全數統一累加收斂於 `settledTotalScore`（Col 5）。
  * **歷年封存與排程標記**：個人 `historySummary`（Col 2）僅保留往年歷史封存分數（如 `"2024"`, `"2025"`）與排程控制標記（`_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`），徹底杜絕在個人帳本寫入當前年份鍵，消除年份鍵污染。
* **2.2 個人貢獻**：`contributionPoints = max(0, settledTotalScore - joinBaseScore)`
  * **個人卓越連動小組總分**：因個人獎勵直接累加至 `settledTotalScore`，組員在組期間獲得個人成就時，個人貢獻分與小組總分同步等額增長，真實帶動小組篇章推進。
  * **入組時間物理截斷**：聖徒未入組前所累積的個人點數，在加入小組時由 `joinBaseScore` 物理錨定截斷，入組瞬間貢獻分嚴格為 0，絕不虛胖灌水至新組。
* **2.3 小組總分**：`GroupTotalScore = GroupHistoryPoints + Σ ActiveMemberContributions`
  * **小組獎勵歷程沉澱**：小組專屬獎勵（晉級篇章點數、退組組員沉澱貢獻分、小組特殊獎勵）呼叫 `depositToHistorySummary` 寫入小組 `historySummary` 當前年份鍵，由 `GroupHistoryPoints` 統一加總。
* **2.4 本機樂觀增量疊加**：`DisplayPoints = AuthoritativePoints + Δ_local`
* **2.5 ProgressLedger 核心總帳模組**：統一封裝快照查詢 (`getPlayerSnapshot`)、歷史積分累加 (`sumHistoryPoints`)、進度行查建 (`findOrCreatePlayerRow`, `findOrCreateGroupRow`)、小組旅程推導 (`getGroupJourney`) 與獎勵發放 (`depositReward`)，全面直連無中介轉發。
* **2.6 進度帳本持久化層架構 (`ProgressLedger` 實體分流與欄位隔離)**：
  * `ProgressLedger.depositReward` 與 `ProgressLedger.batchApplyMilestoneSettlements` 實施嚴格實體欄位分流：
    * **個人獎勵 (`PLAYER`) 寫入 Col 2~5（矩陣寬度 4）**：
      * 寫入矩陣：`[JSON.stringify(historySummary), JSON.stringify(milestones), updatedAt, settledTotalScore]`。
      * Col 5 實體更新為最新結算分 `newSettledScore`（優先取用 `updatedSettledTotalScore`，或安全回退為 `baseSettled + totalRewardPoints`）。
      * **嚴格物理隔離 Col 6 (`joinBaseScore`)**：寫入範圍限定為第 2 欄至第 5 欄（寬度 4），第 6 欄入組基準分完全不受寫入觸碰，徹底捍衛歷史截斷算分不變量。
      * 同步更新記憶體字典快照 `pInfo.settledTotalScore = newSettledScore`，保障同批次記憶體與落盤零漂移 (Zero Drift)。
    * **小組獎勵 (`GROUP`) 寫入 Col 2~4（矩陣寬度 3）**：
      * 寫入矩陣：`[JSON.stringify(historySummary), JSON.stringify(milestones), updatedAt]`。
      * 獎勵點數呼叫 `depositToHistorySummary` 寫入 `historySummary` 當前年份鍵。
    * **實體憑證寫入 (`TaskClaims`)**：
      * 批次持久化階段一次性將所有新產生的憑證矩陣（`claimKey, targetId, taskId, claimedAt`）寫入 `TaskClaims` 工作表（由逐筆 append 降為單次 `getRange.setValues`），支援審計對帳與防重複領取。

## 3. 午夜結算排程引擎 (`runDailyMilestoneSettlement`)

* **唯一官方進入點**：`runDailyMilestoneSettlement(e, forceCalcMeeting)` 作為唯一 Time-driven Trigger 進入點，直連 `SettlementCoordinator.executeDailySettlement`。
* **3.1 多日斷層安全追溯迴圈 (Catch-up Loop)**：
  * 當伺服器排程漏跑 2 天以上時，透過 `SettlementEngine.resolveCatchupDates(lastSettledDate, targetDate, 7)` 自動產出按時間排序的日期追溯序列。
  * 以迴圈依序執行單日結算（每一日均嚴格滿足 `isNextDay === true`），平滑推進 `_lastSettledDate`，安全補發斷層期間的打卡點數與連勝推進。
* **3.2 四階段分流管線**：
  * **階段一**：整表單次批次載入（消除 N+1 I/O）。
  * **階段二**：以小組為單位預算晨興/探訪團體資格（複雜度降為 $O(N)$）。
  * **階段三**：以成員為單位增量計算（檢查 `_lastSettledDate` 提早短路跳過，單次批次回寫）。
  * **階段四**：里程碑批次判定與同晚小組篇章連動 (`MilestoneCoordinator.runBatchMilestoneSettlement`)：
    * **時序 1：聖徒個人評估 (`PLAYER`)**：
      - 依序遍歷在籍聖徒執行 `MilestoneEngine.evaluate`。
      - 當個人達成里程碑獲獎時（`pDec.hasChanges && pDec.totalRewardPoints > 0`）：
        - 即時累加個人記憶體分數：`pRowInfo.settledTotalScore = pDec.updatedSettledTotalScore`。
        - 防禦性標記 `pDec.updatedSettledTotalScore = pRowInfo.settledTotalScore`，杜絕任何重複加分。
        - **同晚小組篇章即時連動 (Zero Lag)**：若組員有所屬小組（`pGid`），即時原子累加小組總分快照 `groupScoreMap[pGid] += Number(pDec.totalRewardPoints)`！
    * **時序 2：小組篇章即時評估 (`GROUP`)**：
      - 緊接著評估小組篇章，小組篇章評估讀取的是**已加計當晚組員個人獲獎增量的小組最新總分** `groupScoreMap[gid]`。
      - 若組員獲得的個人獎勵推動小組總分突破篇章門檻，**同晚立即解鎖小組新篇章**，徹底消除舊架構隔日才解鎖的體驗延遲。
    * **時序 3：單次批次矩陣持久化 (`ProgressLedger.batchApplyMilestoneSettlements`)**：
      - 一次性寫入 `TaskClaims` 實體憑證（個人與小組獲獎憑證一次落盤）。
      - 分流矩陣寫入 `PlayerProgress`（Col 2~5，寬度 4）與 `GroupProgress`（Col 2~4，寬度 3）。
* **3.3 聚會每日增量差集結算 (Weekly Incremental Delta) 與發光金邊固化**：
  * **制度變革**：徹底廢除舊制「每週一才結算上週聚會」的延遲模式，全面整併入「每日午夜增量結算」。昨日聚會打卡，今日清晨點數立即到帳！
  * **極簡資料模型 (`historySummary`)**：
    在 `PlayerProgress` 的 `historySummary` 根節點平鋪紀錄（排程控制鍵與歷年封存）：
    ```json
    {
      "2025": 1250,
      "_lastSettledDate": "2026-10-14",
      "_settledWeekKey": "2026-W42",
      "_settledMeetings": ["smallGroup", "lordDayMeeting"]
    }
    ```
    > [!NOTE]
    > 在重構後的架構中，`PlayerProgress` 當年度點數全數收斂至 Col 5 `settledTotalScore`，`PlayerProgress.historySummary` 僅保留往年封存分數（如 `"2025"`）與排程控制鍵（`_lastSettledDate`, `_settledWeekKey`, `_settledMeetings`），不再包含當年度年份鍵；小組 `GroupProgress.historySummary` 則持續儲存當年度歷程累積（含解鎖篇章獎勵與離隊組員沉澱貢獻）。
  * **集合差集比對演算法**：
    1. **跨週重置**：若排程目標週次 `targetWeekKey !== _settledWeekKey`，更新 `_settledWeekKey = targetWeekKey` 並重置 `_settledMeetings = []`。
    2. **同週差集計分**：比對當日 `MeetingMatrix` 解包打卡項目與 `_settledMeetings`，僅針對差集（新打卡且未曾結算入帳之項目）核發點數增量，並將該項目追加至 `_settledMeetings`。
    3. **結算即固化 (Settled-and-Locked)**：已入帳項目透過 `solidifiedItems` 回傳前端，卡片套用尊榮發光金邊，鎖定撤回操作，防止退轉扣分骨牌效應。

## 4. 里程碑判定引擎與滑動視窗雙條件演算法

### 4.1 MilestoneEngine 核心架構與純領域分流 (Pure Domain Routing)

* **4.1.1 呼叫簽名與快照契約**：
  * `MilestoneEngine.evaluate(snapshot, rules, options)` 採**純領域運算（Pure Domain Logic / Zero I/O）**，不依賴試算表或外部環境，專注在記憶體決策物件的產出。
  * **輸入快照規格 (`snapshot`)**：
    ```javascript
    {
      targetId: string,              // 評估對象 ID (playerId 或 groupId)
      targetType: 'PLAYER' | 'GROUP',// 評估目標類型
      historySummary: Object,        // 歷史歷程摘要字典
      currentMilestones: Array,      // 當前已達成里程碑清單
      settledTotalScore: number,     // 基準結算分數 (baseSettledScore)
      practiceHistory: {             // 操練歷史直欄切片 (零 I/O 記憶體讀取)
        startDate: string,
        dailyRecords: Object.<string, number>,
        meetingRecords: Object.<string, number>
      },
      playerProfile: Object | null,  // 聖徒屬性檔
      groupProfile: Object | null,   // 小組屬性檔
      groupTotalScore: number,       // 小組最新總分
      groupProgress: Object | null   // 小組進度快照
    }
    ```
* **4.1.2 回傳決策物件規格 (`decision`)**：
  ```javascript
  {
    targetId: string,
    targetType: 'PLAYER' | 'GROUP',
    evalDateStr: string,
    settlementDateStr: string,
    hasChanges: boolean,
    newMilestones: Array<MilestoneItem>,
    newClaims: Array<ClaimItem>,
    totalRewardPoints: number,
    updatedSettledTotalScore: number, // ★ 個人累加後結算分 (baseSettledScore + totalRewardPoints)；小組時維持 baseSettledScore
    updatedHistorySummary: Object,    // ★ 小組獲獎寫入年份鍵；個人獲獎保持原快照不變
    updatedMilestones: Array<MilestoneItem>,
    adminLogs: Array<AdminLogItem>
  }
  ```
* **4.1.3 純領域分流演算法 (Zero I/O Routing Algorithm)**：
  ```javascript
  const baseSettledScore = Number(snapshot && snapshot.settledTotalScore) || 0;
  const isGroup = (targetType === 'GROUP');
  const updatedSettledTotalScore = isGroup ? baseSettledScore : (baseSettledScore + totalRewardPoints);
  const updatedHistorySummary = (isGroup && totalRewardPoints > 0)
    ? this.depositToHistorySummary(historySummary, totalRewardPoints, opt.currentYearStr || settlementDateStr.slice(0, 4))
    : historySummary;
  ```
  * **`PLAYER` 分流**：
    - `totalRewardPoints` 累加至 `updatedSettledTotalScore`。
    - `updatedHistorySummary` 保持原快照傳入值不變，不再將個人獎勵寫入年份鍵。
  * **`GROUP` 分流**：
    - `updatedSettledTotalScore` 維持基準分。
    - 獲獎點數呼叫 `depositToHistorySummary` 累加至 `updatedHistorySummary` 年份鍵。
  * **邊界防禦原則**：
    - 若 `!targetId` 提早返回，回傳物件嚴格包含 `updatedSettledTotalScore: Number(snapshot && snapshot.settledTotalScore) || 0`。
    - 數值嚴格轉型與 `|| 0` 防護，全面杜絕 `NaN` 逃逸。

#### 複合條件（Composite AND Conditions）語法與參數路由
`MilestonesConfig` 的 `conditionType` 欄位支援以**空格**、逗號 `,`、加號 `+` 或 `AND` 串接多個條件代碼（例如 `"ALL_WEEKLY_MEETING DAILY_PRACTICE_WEEK_COUNT"`）：
* **短路求值**：由左至右逐一檢驗，所有子條件全數滿足 (AND) 方為達標；任一條件未達成立即中斷並回傳 `false`。
* **參數路由模式**：
  1. **扁平模式**（各條件參數鍵名不衝突）：直接平鋪 JSON，如 `{"includeOutreach": false, "morning": 5, "bible": 6}`。
  2. **命名空間模式**（參數鍵名重疊時）：以條件代碼為頂層 Key，如：
     ```json
     {
       "DAILY_PRACTICE_STREAK": { "item": "morning", "streakDays": 7 },
       "DAILY_PRACTICE_WEEK_COUNT": { "morning": 5, "bible": 6 }
     }
     ```

### 4.3 Streak 連勝里程碑【滑動視窗雙條件演算法】(Sliding-Window Dual-Condition)
* **解決痛點**：原餘數法 (`streak % n === 0`) 要求連續次數必須精確等於 $n$ 的倍數。若遇排程漏跑隔日恢復時 $streak = n + 1$，因 $(n+1) \pmod n \ne 0$，寶箱將被永久漏發。
* **新演算法核心原則**：【最近 $n$ 次是否有連續】且【最近 $n$ 次沒有得過此寶箱】：
  1. **條件一（連續門檻）**：$streak \ge n$。
  2. **條件二（視窗冷卻）**：
     * 日操練：視窗為 $[targetDate - (n - 1), targetDate]$，比對成就 ID 後綴日期。
     * 週聚會：視窗為最近 $n$ 週 $[weekKey - (n - 1), weekKey]$，比對成就 ID 後綴週次。
     * 視窗內已存在領取記錄 $\implies$ 冷卻中（返回 `false`）；未曾領取 $\implies$ 返回 `true`。
* **領域隔離最小注入原則**：
  * 個人成就 (`targetType === 'PLAYER'`)：上下文僅注入至 `playerProgress`。
  * 小組成就 (`targetType === 'GROUP'`)：上下文僅注入至 `groupProgress`。

### 4.4 循環週期模式 (`repeatCycle`)
* `ONCE`：一生一次／永久達成（`effectiveId = rule.id`），八大篇章強制為此模式。
* `REPEAT` / `DAILY`：每日循環（`effectiveId = rule.id + '_' + dateStr`）。
* `WEEKLY`：每週循環（`effectiveId = rule.id + '_' + weekKey`），當週內首度達標即頒發憑證，同週後續天數自動冪等略過。

## 5. 八大篇章與成就寶箱架構

### 5.1 篇章門檻階梯體系（彼得後書八步梯 50,000 點權威標準）
系統前後端統一採用彼得後書八步梯階梯門檻：
1. 信心篇：初始起點 (0 點)
2. 美德篇：2,000 點
3. 知識篇：5,500 點
4. 節制篇：10,000 點
5. 忍耐篇：16,000 點
6. 敬虔篇：24,000 點
7. 弟兄相愛篇：35,000 點
8. 愛篇：50,000 點
* **進度百分比計算模型**：
  * **單篇章區間進度 (Intra-Chapter Progress)**：以當前目標篇章之起訖門檻計算：
    $$\text{percent} = \max\left(0, \min\left(100, \text{round}\left(\frac{\text{totalScore} - \text{prevTarget}}{\text{currentTarget} - \text{prevTarget}} \times 100\right)\right)\right)$$
  * **全篇章解鎖進度 (Global Journey Progress)**：以已完成篇章數除以總篇章數：
    $$\text{progressPercent} = \text{allPassed} \mathbin{?} 100 : \min\left(100, \text{round}\left(\frac{\text{completedChapters.length}}{\text{totalChaptersCount}} \times 100\right)\right)$$
* **篇章 Gap 差距模型**：$\text{gap} = \max(0, \text{targetPoint} - \text{groupTotalPoints})$。
* **小組總分與篇章旅程推導 (`getGroupJourney`) 之端到端對齊**：
  * **首頁與旅程數據一體化**：首頁右上角點數面板上半部呈現之小組點數 `groupTotalPoints`，與首頁彼得後書八步梯橫向拖曳軌道（`chapterScrollTrack`）及「活力組旅程」彈窗（`openGroupJourneyListModal`）所依據的旅程分數 `journeyPoints`，**100% 來自相同之權威小組總分 `GroupTotalScore`**。
  * **未入組邊界保護**：未加入小組之聖徒，篇章旅程軌道處於未激活狀態，首頁上半部卡片顯示 `"---"`（單位隱藏）；加入小組後，以物理截斷基準分 `joinBaseScore` 起算個人貢獻，組員在籍期間所累積之操練與里程碑獎勵點數，即時帶動 `GroupTotalScore` 前進，首頁小組卡片與篇章進度條同步等額躍升。

### 5.2 成就與寶箱獲得模式收斂
* **單一履約模式**：確立「被動排程結算 + 登入增量慶祝」為唯一模式。
* **廢棄主動領取**：徹底廢除前端與後端主動 `claimChest` RPC，全系統成就統一記錄於 `milestones` 陣列中，消除歷史 `claimedChests` 雙軌維護負擔。
* **秘密成就防劇透**：未達成且 `isHidden === true` 時，前端遮蔽顯示為「??? 秘密成就」。

### 5.3 生產端 Fallback 清除規範
* `ChapterConfig` 與 `AchievementConfig` 當工作表不存在或為空時，一律嚴格回傳空陣列 `[]`，徹底清除代碼中硬編碼的 fallback 陣列，保證試算表配置為唯一真理來源。

### 5.4 實體履約憑證架構 (`TaskClaims`)

* **實體存證定位**：微服務 C 成就與篇章履約的唯一不可變存證總表 (`TaskClaims`)，提供審計對帳與跨夜防重複發放防線。
* **資料表結構 (Col A ~ Col D)**：
  | 直欄 | 欄位代碼 | 資料型別 | 說明與資料範例 |
  |:---:|:---|:---:|:---|
  | **Col A** | `claimKey` | `string` | 複合防重複發放主鍵（`${targetId}_${taskId}`，如 `P01_MLS_P_BIBLE`, `G01_CHP_VICTORY_LV2`） |
  | **Col B** | `targetId` | `string` | 獲獎主體 ID（聖徒 `playerId` 或活力組 `groupId`） |
  | **Col C** | `taskId` | `string` | 里程碑或篇章規則有效 ID (`effectiveId`) |
  | **Col D** | `claimedAt` | `string` | 履約獲獎時間戳 (ISO-8601) |
* **全鏈路憑證生成與持久化流水線**：
  1. **日常個人里程碑與連勝寶箱**：`MilestoneEngine.evaluate` 判定通過時產出 `newClaims` 陣列。
  2. **小組篇章晉級憑證**：小組總分達標解鎖新篇章時，即時產出小組篇章 `claimKey`。
  3. **批次單次矩陣落盤**：`ProgressLedger.batchApplyMilestoneSettlements` 一次性將當晚全體聖徒與小組之新憑證成批寫入 `TaskClaims` 工作表，從數百次 RPC 降為單次 `getRange.setValues`。
  4. **管理員特殊發放 (`grantTargetedReward`)**：管理員手動針對個人或小組發放特殊獎勵時，同步落盤 `TaskClaims` 憑證與 `AdminLogs` 審計日誌。
