# 文檔四：專案整體架構書

> **目的**：讓接手者理解全系統架構拓撲、通訊原理、微服務邊界、安全防禦機制與資料流動路徑。

---

## 1. 全系統架構拓撲

* **架構全景圖**：SPA 前端 ↔ Iframe RPC Bridge ↔ 三 GAS 微服務 ↔ 三 Google Sheets 物理庫
* **前後端職責邊界與 PWA 快取**：
  * **前端 (SPA Client, PWA)**：基於原生 HTML5/CSS3/Vanilla JS，搭載 Service Worker（快取版本 `vital-cache-v104`，靜態資源查詢字串 `?v=20261014-v104`）與 Web Storage，實現 0ms 離線秒開、樂觀即時交互、待結算點數試算與首頁雙點數視覺映射。
  * **後端 (GAS Microservices)**：Core (核心業務)、Chat (小組交流)、Progression (成就履約) 三物理微服務，負責業務規則校驗、無鎖單格高頻直寫、原子名冊鎖定、留言矩陣維護與深夜批次權威結算。
* **資料庫選擇 Google Sheets**：零基礎設施維護成本、天然審計軌跡、直觀視覺化、容量足夠 500 人在職聖徒運行 3 年以上。
* **三微服務物理隔離**：
  * **Core (核心業務庫)**：每日操練打卡核心。打卡直寫**100% 絕對無鎖**（20~50ms 單格秒寫）；用戶註冊與成員離隊則具備 10 秒 `LockService` 排他鎖保護名冊原子性。
  * **Chat (小組交流庫)**：交流板高頻發言。配置**專屬 3000ms 微鎖等待逾時**（單元格追加之鎖持有耗時僅約 20~50ms），一組一快取，防止打卡執行緒被留言阻塞。
  * **Progression (成就履約庫)**：成就、篇章與履約。負責深夜密集批次運算與排程，完全隔離日常業務。

## 2. 三微服務詳細職責與跨庫協同

* **微服務 A — Core (核心業務庫)**
  * 生產檔案：`dist/core/Code.gs`, `dist/core/Bridge.html`
  * 職責：聖徒註冊登入、Session 鑑權、操練與聚會打卡、活力組生命週期、足跡統計、公告廣播。
* **微服務 B — Chat (小組交流庫)**
  * 生產檔案：`dist/chat/Code.gs`, `dist/chat/Bridge.html`
  * 職責：直欄矩陣時序留言、組長一則永久置頂公告、45s 輪詢快取穿透 (HTTP 304 模擬)。
* **微服務 C — Progression (成就履約庫)**
  * 生產檔案：`dist/progression/Code.gs`, `dist/progression/Bridge.html`
  * 職責：點數總帳、深夜排程斷層安全結算、八大篇章推導、10 階成就判定、TaskClaims 帳本。
  * **模組分層架構與職責劃分**：
    * **純領域里程碑引擎 (`MilestoneEngine`)**：Zero I/O 純領域計算。負責成就與篇章規則判定，並實施**純領域獎勵分流**：個人獎勵 (`PLAYER`) 累加至決策物件之 `updatedSettledTotalScore` 出參（歷程年份鍵保持純淨）；小組獎勵 (`GROUP`) 寫入小組 `updatedHistorySummary` 年份鍵。
    * **進度帳本持久化層 (`ProgressLedger`)**：專責二維矩陣落盤與記憶體狀態同步。`depositReward` 與 `batchApplyMilestoneSettlements` 針對個人進度精準以 Col 2~5（寬度 4）批次寫入，同步刷新 Col 5 `settledTotalScore`，對 Col 6 `joinBaseScore` 實施**物理隔離**；小組獎勵維持寫入 Col 2~4（寬度 3）。
    * **深夜批次協調器 (`MilestoneCoordinator`)**：排程時序協調，管線內組員獲獎時**同晚即時加算** `pRowInfo.settledTotalScore` 與 `groupScoreMap`，緊接著的小組篇章評估即時感知最新總分並當晚直接突破解鎖新篇章。
    * **歷史遷移治理**：歷史遺留於 `historySummary["2026"]` 之個人獎勵已由獨立遷移程序順利轉移至 Col 5 `settledTotalScore`，且過渡函數已完全清理，代碼庫維持零死代碼。
* **跨服務協同機制（Shared-Database Pattern）**：
  * 受限於 Google Apps Script 無內部私有網路 RPC 之特性，微服務間協同透過後端 Gateway 模式（如 `ProgressionGateway`、`ChatGateway`、`CoreGateway`），由服務帳號授權透過 `SpreadsheetApp.openById()` 跨庫讀寫物理分頁。
  * 所有跨庫調用均包含於獨立的 `try-catch` 降級防禦中，主服務絕不因跨庫寫入異常而中斷客戶端回應。

## 3. 前後端通訊層與入站正規化

* **通訊痛點**：GAS Web App 的 302 跨域重定向導致前端直接 `fetch()` 延遲飆升且引發 CORS 錯誤。
* **解決方案**：隱藏 `Bridge.html` 嵌入各微服務，透過 `window.postMessage` 與客戶端通信。
* **就緒握手協議**：
  1. Bridge 載入時主動向父層廣播：`postMessage({ type: 'GAS_BRIDGE_READY', service: 'CORE' }, '*')`。
  2. 前端 `ApiClient` 註冊通道就緒（逾時上限 15 秒）；
  3. 前端派發請求：`postMessage({ type: 'GAS_CALL', id, action, token, data }, '*')`；
  4. Bridge 呼叫 `google.script.run`，完成後以 `postMessage({ type: 'GAS_RESPONSE', id, ... }, '*')` 回傳。
* **入站參數正規化架構 (`normalizeInboundParams_`)**：
  * **Core / Progression**：透過 `normalizeInboundParams_(payload)` 統一解包。Core 實作了頂層屬性與 `payload.data` 的無感融合（`Object.assign`），Progression 優先解構 `data` 容器。
  * **Chat**：採用特化解析器 `adaptInboundRequest_(request)`，直接提取留言專屬欄位。
* **標準信封規範**：
  * 請求信封 `CanonicalPostRequest`：`{ action, token, data, requestId }`
  * 成功回應信封 `CanonicalSuccessEnvelope`：`{ success: true, code: 'OK', data: T, status: 200, respondedAt }`
  * 失敗回應信封 `CanonicalErrorEnvelope`：`{ success: false, code: string, error: string, message: string, status: number, respondedAt }`

## 4. 全域安全架構與防禦機制

### 4.1 IDOR 水平越權雙向校驗機制 (`resolveAuthenticatedPlayerRow_`)
為兼顧 Google Sheets 讀寫效能與防止行號竄改越權，實作雙向校驗機制：
* **Fast-Path ($O(1)$)**：當客戶端傳入 `matrixColIndex` 作為定位提示行號時，後端僅讀取該指定行的第一欄（`playerId`）。比對相符（正常情況）直接放行，保留快取秒開優勢。
* **Fallback**：若比對不符（遭竄改、資料移位或快取過期），安全回退至全表定位該已認證玩家之真實行號，100% 杜絕惡意傳入他人行號越權竄改小組綁定或個資。
* **全面覆蓋**：應用於建組、加入小組、退組、轉讓隊長、更名、更換頭像與修改密碼等端點。
* **Chat 留言板直欄校驗**：Chat 微服務之 `getGroupColNum_` 同樣實作以 `postsColIndex` 驗證首列 `groupId` 之防偽機制。

### 4.2 認證防禦與密碼安全
* **防暴力破解鎖定 (Rate Limiting)**：利用 `CacheService` 記錄連續登入失敗次數，同一帳號失敗達 5 次時自動鎖定 15 分鐘，防禦字典檔暴力攻擊。
* **加鹽雜湊雙向相容**：徹底廢除明文密碼比對回退，全面強制 SHA-256 加鹽雜湊，後端相容 64 碼 Hex 與 44 碼 Base64 格式。
* **並發註冊與退組排他鎖**：註冊端點 (`registerUserInSheet_`) 與退組端點 (`leaveVitalGroup`) 全面引入 `LockService.getScriptLock().waitLock(10000)` 序列化排他保護，杜絕多人同時掃碼註冊時覆蓋資料與直欄座標錯位。
* **試算表公式注入防禦 (Formula Injection)**：寫入 Sheets 之所有使用者輸入欄位（如姓名、暱稱、帳號）前置 `@` 純文字格式保護，防止試算表惡意公式執行。
* **前端在途動作互斥鎖 (In-Flight Action Mutex)**：`apiClient.js` 針對破壞性動作（`joinGroup`, `postMessage`, `updateAvatar` 等）設定記憶體互斥鎖，避免短時間重複點擊重複送出。

### 4.3 帳本持久化物理隔離與數值防護
* **Col 6 `joinBaseScore` 物理隔離**：在 `ProgressLedger.depositReward` 與 `batchApplyMilestoneSettlements` 中，個人進度寫入嚴格指定 `getRange(row, 2, 1, 4)` 涵蓋 Col 2~5（歷程、里程碑、更新時間、結算總分），從 Sheet API 底層物理隔絕 Col 6 入組基準分，保障入組時間截斷點不被覆蓋。
* **數值型別防護與 NaN 防禦**：所有積分計算（`settledTotalScore`, `totalRewardPoints`, `groupScoreMap` 累加）全面使用 `Number(...) || 0` 型別轉換與回退防禦，杜絕字串拼接或 `NaN` 逃逸污染資料庫。

## 5. 全域資料流向

* **登入與冷啟動水合流**：本地 localStorage 0ms 秒開繪製 ➔ 背景發起 `getPractice()`（極速解鎖打卡）與 `getBootstrap()`（全量資料水合）。
  * **首頁雙點數狀態呈現 (`.hero-score-grid`)**：
    * **上半部（小組整組累積總點數卡 `hero-group-score`）**：
      * 無小組狀態：數值顯示 `"---"`，單位「點」（`homeGroupScoreUnit`）透過 `hidden` 屬性物理隱藏。
      * 有小組狀態：動態綁定全組累積總點數 `groupTotalPoints`（以千分位格式輸出，如 `3,280`），單位「點」移除 `hidden` 正常呈現。
      * 視覺規格：桃紅色系 `#d66b91`、字級 `28px !important`、字重 `1000`。
    * **下半部（個人整年累積總點數卡 `hero-personal-score`）**：
      * 動態綁定個人整年權威結算總點數 `personalPoints`（Col 5 `settledTotalScore` + 歷史年度累積沉澱分），含個人里程碑與個人特殊獎勵。
      * 視覺規格：青綠色系 `#2f8f7e`、字級 `28px !important`、單位「點」。
      * 相容性維護：節點內部保留隱藏之 `homeContributionText` 與 `homeContributionSyncText` 同步更新 `contributionPoints`，維持既有外部調用與測試契約。
    * **點擊行為統一導流**：無論使用者點擊上半部或下半部卡片，點擊事件均由父層網格委託派發 `onContributionClick` 呼叫 `profileView.openContributionModal()`，統一打開「同行貢獻面板」，清晰展開個人入組前基準點、在籍貢獻點與小組全體成員貢獻明細。
    * **零本地偽結算 (Zero Pseudo-Settlement)**：正式點數嚴格呈現後端權威值，當日打卡與當週聚會未結算分由純前端領域引擎 `PendingPointsEngine` 獨立試算為待結算膠囊（Pending Chips），不擅自累加至正式點數，防止跨裝置飄移。
* **操練打卡流**：UI 10ms 樂觀打勾 ➔ `OptimisticPracticeStore` 細粒度欄位突變追蹤 ➔ Base-100 佇列收斂 ➔ 後端無鎖單格直寫 ➔ 失敗進入離線佇列 (`vital_offline_queue`) 標記琥珀燈。
* **交流發言流**：發布留言 ➔ 前端互斥鎖防連擊 ➔ Chat 微服務原子追加至直欄末尾 ➔ ScriptCache 失效。
* **深夜排程結算流 (Nightly Settlement Pipeline)**：
  1. **觸發與追溯**：凌晨 03:00~04:00 Time-driven Trigger 啟動 ➔ Progression 多日斷層安全追溯序列（Catch-up Loop）。
  2. **每日打卡與聚會結算**：每日操練全勤/連續天數結算 ➔ 聚會當日增量差集核發（`_settledMeetings` 差集比對並固化發光金邊）➔ 批次回寫至 `PlayerProgress`。
  3. **里程碑與篇章批次結算 (`MilestoneCoordinator.runBatchMilestoneSettlement`)**：
     * **個人里程碑純領域評估 (`MilestoneEngine.evaluate`)**：以單次批次快照進行規則判定，個人獎勵純領域累加至決策物件之 `updatedSettledTotalScore` 出參，個人歷程 `historySummary` 保持純淨。
     * **組員獲獎同晚即時連動 (Zero-Lag Sync)**：當組員達成個人里程碑獲獎時，即時累加個人記憶體分數，並就地累加小組總分快照 `groupScoreMap[pGid] += rewardPoints`。
     * **小組篇章即時解鎖**：緊接著執行小組篇章評估，因小組總分已即時納入當晚組員個人獎勵，達標時同晚直接解鎖新篇章，消除隔日解鎖延遲。
     * **實體隔離批次持久化 (`ProgressLedger.batchApplyMilestoneSettlements`)**：個人獎勵以寬度 4 精準批次回寫 `PlayerProgress` Col 2~5（更新 Col 5 `settledTotalScore`，嚴格物理隔離保護 Col 6 `joinBaseScore`；小組獎勵寫入 `GroupProgress` Col 2~4），並批次追加 `TaskClaims` 履約憑證。
  4. **點數守恆與沉澱閉環**：個人獎勵進入 Col 5 帶動個人小組貢獻分 $\max(0, \text{settledTotalScore} - \text{joinBaseScore})$ 與小組總分同步增長；入組時 `joinBaseScore` 基準錨定杜絕回溯灌水；退組時個人貢獻分全額沉澱至舊組 `historySummary`，點數守恆不失分。
* **足跡與歷史資料流**：本地快取 0ms 秒開 ➔ 背景 `getFootprints` SWR 觸發 ➔ 後端單次 Bounding-Box 提取原始 Base-100 矩陣 ➔ 前端聚合計算。

## 6. 核心架構原則

* **深層模組 (Deep Module)**：提供窄而精確的介面，內部消化極端複雜度。
* **核心無鎖 (Zero-Lock Core)**：操練打卡採用直欄座標直接寫入，消除鎖競爭超時。
* **樂觀更新 (Latest-Wins Optimistic UI)**：後令覆前令，細粒度欄位保護，杜絕幽靈復活。
* **離散成員最小包圍區間批次讀取 (Bounding-Box Batch Seam)**：嚴禁迴圈逐欄 API 調用，所有 I/O 均以二維陣列單次批次完成。
* **純領域與持久化解耦 (Pure Domain & Persistence Decoupling)**：領域判定引擎 (`MilestoneEngine`) 零 I/O 依賴，僅輸出乾淨決策物件；持久化層 (`ProgressLedger`) 專責矩陣落盤與記憶體狀態同步，杜絕狀態漂移。
* **點數守恆與物理隔離 (Point Conservation & Physical Column Isolation)**：
  * 個人成就與特殊獎勵計入當年度結算分 (`settledTotalScore` Col 5)，透過 $\max(0, \text{settledTotalScore} - \text{joinBaseScore})$ 自然連動個人小組貢獻分與小組總分。
  * 矩陣持久化以 Col 2~5（寬度 4）精準寫入，物理隔離 Col 6 `joinBaseScore` 入組基準分，杜絕覆蓋歷史截斷點。
  * 聖徒入組基準自動錨定防止入組前點數回溯灌水；退組時個人貢獻分全額沉澱至舊組歷程 (`historySummary`)，實現全生命週期點數嚴格守恆。
* **極簡治理與零死代碼 (Ponytail Minimalist Governance & Zero Dead Code)**：歷史資料一次性遷移完成後，立即將過渡函數與頂層進入點自生產代碼徹底拔除，維持代碼庫極致精簡，排程日常管線不留任何多餘過渡邏輯。
* **權威水合與零偽結算 (Authoritative Hydration & Zero Pseudo-Settlement)**：前端各視圖（首頁雙點數卡、同行足跡、個人中心）嚴格呈現後端回傳之權威分數，不於本機私自進行樂觀累加，當日打卡與當週聚會增量由純前端領域引擎 (`PendingPointsEngine`) 獨立試算為待結算膠囊（Pending Chips），消弭跨裝置數值分歧與幽靈點數。
* **版本號治理與雙層快取失效機制 (Cache Eviction Protocol)**：PWA 核心 `sw.js` 快取名稱（全面升級至 `vital-cache-v104`）與 `index.html` 引用之靜態資源查詢字串（`?v=20261014-v104`）實施雙層強同步遞增機制，確保新版本發布時客戶端能精準觸發 Service Worker 快取淘汰，消弭舊資源快取黏滯。
* **測試防護網與工程基準 (Testing Safety Net & Regression Baseline)**：全系統建立 589/589 PASS 之自動化單元與整合測試基準（`node --test tests/**/*.test.js`），包含專項測試 `tests/unit/homeScorePanelRefactor.test.js`，針對首頁點數面板無組/有組狀態、統一彈窗導流、在線即時刷新及點數守恆機制實施 100% 迴歸防護。
