## 🎯 核心架構與最新重構摘要（2026-10-16 狀態）

### 1. 後端三大微服務與物理試算表
- **微服務 A (Core 核心業務)**：`dist/core/Code.gs` + `Bridge.html` ➔ 對應【核心業務試算表】（操練打卡、活力組管理、個人資料、IDOR 雙向校驗）。操練打卡 100% 絕對無鎖，註冊與退組有 10s `LockService` 保護。
- **微服務 B (Chat 小組交流)**：`dist/chat/Code.gs` + `Bridge.html` ➔ 對應【小組交流試算表】（直欄矩陣高頻留言板、組長公告、XSS 實體轉義、3000ms 微鎖逾時）。
- **微服務 C (Progression 成就履約)**：`dist/progression/Code.gs` + `Bridge.html` ➔ 對應【成就履約試算表】（深夜排程多日追溯結算、個人獎勵計入 Col 5 `settledTotalScore` 與同晚小組篇章即時連動、Streak 滑動視窗、`ProgressLedger` 總帳管理）。
- **全系統實體狀態全面收斂為 `ACTIVE` / `INACTIVE` 二元狀態**：
  除 `AreaMappings` 維持布林值 `isEnabled` 外，全系統分頁（`Players`、`Groups`、`Announcements`、`MilestonesConfig`、`ChapterConfig`、`AchievementConfig`、`TasksConfig`）之狀態欄位全面淘汰歷史割裂詞彙（`SUSPENDED`、`DISBANDED`、`ARCHIVED`、`DELETED`），統一收斂為權威 `INACTIVE`，線上 Google Sheets 歷史資料與使用說明已同步完成批次清洗。

### 2. 個人獎勵計入 Col 5 與小組總分連動架構（點數守恆與年度沉澱）
- **個人獎勵直接累加至 Col 5 `settledTotalScore`**：
  - 個人里程碑、成就寶箱、個人特殊任務獎勵，由原先寫入 `PlayerProgress.historySummary["2026"]`（Col 2）改為直接累加至 Col 5 `settledTotalScore`，杜絕歷年年份鍵污染。
  - 持久化層 `ProgressLedger.depositReward` 與 `batchApplyMilestoneSettlements` 精準寫入 Col 2~5（欄寬 4），並嚴格物理隔離 Col 6 `joinBaseScore`。
- **小組總分與個人在籍貢獻分即時連動**：
  - 個人在籍貢獻分公式：$$\text{contributionPoints} = \max(0, \text{settledTotalScore} - \text{joinBaseScore})$$
  - 小組總分公式：$$\text{groupTotalPoints} = \text{sumHistoryPoints(Group Col 2)} + \sum_{m \in \text{ActiveMembers}} \text{contributionPoints}_m$$
  - 個人獲得之所有個人獎勵直接帶動個人貢獻分與所屬小組總分同步增長。
- **點數守恆定律全生命週期閉環**：
  - **入組前不回溯**：未入組聖徒獲獎後加入活力組，`joinBaseScore` 自動錨定當時之 `settledTotalScore`，入組時個人貢獻分嚴格為 0，入組前獎勵不灌水給新組。
  - **入組後同心累積**：在組期間之每日操練、個人里程碑與個人特殊獎勵，同步帶動個人貢獻分與小組總分。
  - **退組自動沉澱**：組員退組時，其在籍貢獻分全額沉澱至舊小組 `GroupProgress.historySummary`（Col 2），舊組總分完全守恆不失分；退組後或轉入新組時，基準分重新錨定為當下 `settledTotalScore`。
- **夜間排程同晚小組篇章即時連動 (`runBatchMilestoneSettlement`)**：
  - 組員達成個人里程碑獲獎時，即時同步個人記憶體分數與小組 `groupScoreMap[pGid]`。
  - 緊接著在同晚執行的小組篇章評估即時感知最新總分，實現「組員同晚獲獎突破門檻、小組同晚直接解鎖新篇章」。
- **歷史個人獎勵一次性遷移落盤與過渡代碼清理**：
  - 生產環境已成功執行 `runMigratePlayer2026Rewards()`，將歷史帳本累積於 `PlayerProgress` Col 2 的 2026 年個人獎勵全數搬移至 Col 5 `settledTotalScore`，清除 `"2026"` 鍵並完好保留往年封存與系統控制欄位。
  - 遷移確認落盤後，過渡遷移函式已從生產代碼中徹底清理，維持代碼庫極致精簡與零 Dead Code。

### 3. 前端架構、通知體系與狀態演算法升級
- **`VitalToast` 輕量化通知系統**：全域淘汰阻塞原生 `alert()`，三段位置、四色主題，無縫委託每週任務待結算與固化提示。
- **`OptimisticPracticeStore` 細粒度欄位突變追蹤**：記錄使用者主動變更欄位，在途狀態 Latest-Wins，隊列清空後以伺服器權威為準，徹底根除打卡撤回時的「幽靈復活」缺陷。
- **全站彈窗無障礙與安全互動**：標準 a11y 宣告、44px 最小觸控熱區、遮罩背景點擊安全退出（不綁定 Escape 鍵）、彈窗背景滾動穿透防禦。
- **GPU 動態效能規範**：發光金邊光暈改採 `::after` + `opacity` 獨立合成層呼吸動效，消除 CPU 逐幀 Repaint 重繪發熱。

### 4. 里程碑條件引擎與屬性檢驗升級（Condition Engine v3.2）
- **刪除 `MANUAL_ADMIN` 條件**：全面淘汰無業務邏輯的佔位條件，杜絕死代碼。
- **新增個人與小組屬性檢驗條件**：
  - `CHECK_PLAYER_PROFILE`：檢驗聖徒個人多項指定屬性（如 `realName`, `gender`, `district` 等）是否皆在表列項目中。
  - `CHECK_GROUP_PROFILE`：檢驗活力組多項指定屬性（如 `memberCount`, `groupName` 等）是否皆在表列項目中。
  - **極簡與健壯性 (Ponytail)**：以標準庫 `every` 與 `some` 取代 50 行手寫巢狀迴圈；支援字串與數值鬆散型別比對、前後空白 `trim()`、大小寫不敏感相容，小組未顯式帶入 `memberCount` 時自動由 `activeMembers.length` 計算。
- **`WEEKLY_MEETING_STREAK` 嚴格整數倍週期與基準日對齊**：
  - 結算目標日基準日統一對齊（避免週一凌晨跨週邊界提前誤領下週寶箱）。
  - 修復連續聚會週數重複領取問題，嚴格依 `streak % n === 0` 或滑動視窗冷卻發放。
